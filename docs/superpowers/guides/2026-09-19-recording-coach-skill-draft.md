## 1. 角色模型：操作员不碰浏览器

录制链上有三个角色，SKILL 必须先固化这个分工：

- **主线程（编排者）**：写任务文本（带门闩）→ `analyze` 切片 → `create` 建交易单 → 派发 → **独立复核落库**（不采信子代理回报，自己再查一遍 DB）。
- **子智能体（操作员）**：只调控制面 API + CDP + MySQL，全程不打开浏览器、不 git commit、不改仓库代码。它的价值 = 自包含任务书 + 全程证据落盘。
- **录制引擎（真正执行者）**：控制面 4097 背后的常驻 Python agent（session_runner + controller/actions），租执行机槽位、起 Chrome、用系统账号登录 SUT、逐阶段操作 Element UI 页面。

操作员是"开机、清场、看守、关机、验收"，不是驾驶者。

## 2. 任务书五段式（提示词模板）

子智能体每次启动都是全新上下文，任务书必须自包含，固定五段：

1. **固定参数**：控制面地址、交易 id、functionId、systemAccountId、**阶段数字 id 数组**（不是 UUID）。
2. **业务目标**：客户名/编号、单据编号、有效期——让操作员知道自己录的是什么业务。
3. **风险预告**：已知的前置风险（如在途授信、评级未生效）+ 处置纪律："若被拒，照实记录原文与流水号即合法终局，不得伪造、不得自行重录"。
4. **管线步骤**：每步 API 路径、curl 超时、证据文件名（见 §3）。
5. **产出契约**：证据目录、报告路径、**结论枚举**（`CREATED_<产物>` / `REJECTED_<原因>` / `BLOCKED_<原因>` / `ERROR`）、最后回报格式（结论一行 + 报告路径 + 3 条关键证据）。

## 3. 管线七步（含实测坑位）

| 步 | 动作 | 坑位/要点 |
|---|---|---|
| 1 | `POST /api/v2/trajectories/:id/record/prepare`（无请求体，**curl 超时 ≥600s**） | 可能挂 10 分钟（租槽位+起 Chrome+登录）；只认响应 `ready=true`，否则停手回报 |
| 2 | 记录槽位：从 executor 状态接口查 remoteSessionId 所在 slotIndex | **CDP 端口 = 19242 + slotIndex** |
| 3 | CDP 预检：`node cdp-precheck.mjs <PORT>` 枚举可见 el-dialog/el-drawer/遮罩并关闭无关弹窗 | 等 30s 页面稳定再跑；可循环重跑直到干净。不清场则 agent 第一步即被挡 |
| 4 | `POST .../record/start`，体 `{"phaseIds":[数字id...]}`，**超时 ≥600s** | ① phaseIds 必须是数据库数字 id，**传 UUID 必 400**；② 建单端点是 `POST /api/v2/trajectories`（无 /create 后缀）；③ 该调用**阻塞**到全部阶段收口 |
| 5 | 值守轮询：每 60s `GET /api/v2/trajectories/:id`，快照落盘 | 操作员只记录不干预；总时长上限 40 分钟防僵死 |
| 6 | `POST .../:id/detach` | 释放 Chrome + Python + 槽位，一样不落（record/stop 不释放槽位） |
| 7 | 落库验收：直查 MySQL `trajectory_phase`/`trajectory_step` | **不认 isSuccessful / recordStatus**；doneLogs 在 executor 源头截断 ~400 字符，尾部不可恢复，勿依赖 |

## 4. 门闩设计（任务文本里的硬约定）

- **每阶段一个落库判据**，未满足不得 done；禁止跨阶段合并。
- **保存/提交类操作以页面真实反馈为准**，禁止伪造成功。
- **诚实失败也是合格交付**：服务端拒绝（评级未生效/在途授信等）时照抄提示原文 + 全局流水号并 done——拒绝原文完整落库本身就是有效验收证据。
- **禁区清单**写进任务书：禁影像上传（空态直接下一步）、禁用信/合同模块、禁撤销/修改既有记录、**禁删除类探针**（#896 教训：agent 顺手做 deleteApply 前端探针虽无网络请求，但贴红线）。
- 已知前置语义（SUT 实测）：有效评级=审批「通过」终态（待发起/审批中/打回都不算）；在途授信校验**连「打回」态也算在途**。

## 5. 派发前自查清单（coach 的核心价值）

录制失败最贵的教训是**前置数据没核就开单**（wet8 一晚三单全被业务前置拒绝）。派发前必查：

1. **业务前置在不在**：评级通过态？有在途授信/在途评级？→ 先派**只读核查员**（只连 MySQL/API，不录制）查证，别信记忆。
2. **执行机槽位空闲**：executor `inUse` 状态。
3. **服务健康**：控制面 4097 心跳、执行机在线。
4. **任务切片合理**：10 阶段以内、每阶段一个页面/一个确认点、阶段描述自带判据（analyze 产出后人工过一遍再 create）。

## 6. 操作员变体（同一骨架）

- **只读核查员**：只查 DB/API/KB，零录制——用于纠"前置已满足"的误判、查候选客户池。
- **取证员**：CDP 截图 + doneLogs 残尾反推——用于截断数据的抢救与现场快照。
- 骨架不变：自包含任务书 + 证据落盘 + 不提交 + 主线程复核；变的是管线步骤与可写文件集（并行子代理文件集必须不相交）。

## 7. 红线（写死在任务书里）

- 子智能体**一律不 git commit/push、不改仓库代码**，主线程验收后代办。
- 未经主线程/用户授权不得新建交易重录。
- 全部 API 响应、轮询快照、日志摘录落盘到证据目录——失败也是数据。
- 主线程独立复核（自己跑 SQL/API）后才写收工结论，不采信子代理单方回报。
