## 一、结论

1. **「能做」已经证明，难点变成「稳、快、可复用」。** 对公主链七环节 09-22 全部走通；客户新增轨迹回放 12 步确认 11 步。但 AI 录制成功率近 45 天约 71%，9 月最后两周约 61%。失败录制的活跃时长中位 7.6 分钟，是成功录制的 3.8 倍。每一步平均调用 1.7–2.2 次模型；需要模型决策的点击中位 15–36 秒，批量填表一步不到 1 秒。

2. **推荐主线：首次探索，此后编译。** 模型只负责第一次走通和出错时接管。验证过的阶段沉淀成确定性的、带参数的执行单元，录制时先执行它，失败再交回模型。登录已经这样运行（`src/services/trajectory/trajectory-record-lifecycle.js:363-409`），导航到功能页也已经确定性执行（`src/services/trajectory/menu-navigation.js`）。v1 把这个做法推广到「跨菜单导航」和「查询并打开记录」两类不写库的阶段，见配套设计稿。

3. **这条主线有两个前提，要先做。**
   - **判定可信。** 成功与否以确定性证据为主，LLM 核验为辅，并且 LLM 核验先用人工标注集校准。部署版 10-03 起让 LLM 断言直接改写录制状态（接口文档称「LLM 断言即标签」）。不校准，成功率数字就无法在版本之间比较，沉淀也会把误判写进资产。
   - **评测闭环。** 用固定任务集给每个开关、每次改动出「做 / 不做」的数字结论。9 月有多项修复已合入但默认关闭，一直在等湿测窗口。

4. **安全是 P0，与功能线并行、立即处理。** SSO 默认关闭（`config/config.js:193`）。LLM 中转 `/v1/chat/completions` 挂在 `/api/v2` 之外，SSO 打开也管不到，并且一律用服务端密钥转发（`src/routes/llm-proxy.js`）。`/ws` 在未配令牌时放行。部署实例要按 3.7 的表逐项核查。在银行业务测试环境里，这一项先于任何功能。

5. **研发体系需要减负。** 08-01 至 09-24 共 2563 个非合并提交，其中 1044 个只改文档（41%）；协作日志约 970 条；门禁脚本 284 个文件约 4.9 万行，抽样约六成只断言源码子串；没有 CI，也没有单元测试框架。迁到 monorepo 是重置的时机：CI 跑冷门禁，补行为级金样例，精简协作协议。

## 三、审查发现

严重度按对成功率、效率、安全的影响定级。

### 3.1 成功率的口径正在漂移（高）

10-03 起 LLM 核验结果直接成为录制状态。它能纠正一部分「自报成功、其实没做成」，但带来三个后果：

- 成功率变化无法归因：是引擎变好了，还是核验器的倾向变了。提示词或模型一换，历史数字就不可比。
- 核验器没有公开的校准数据。9 月报告引用的研究结论是：评判结构（过程与结果分开打分、不采信 agent 自述）比换更强的模型更重要。
- 被翻成 failed 或 recorded 的轨迹会进入后续统计与沉淀，误判会被放大。

建议把「成功」拆成四层，同时报告：

| 层 | 定义 |
|---|---|
| L0 | 录制状态为 recorded |
| L1 | 确定性业务证据成立：单据号或业务 stamp、成功 toast、接口 2xx、预期页面跳转 |
| L2 | 录后回放通过（先只覆盖不写库的阶段） |
| L3 | 人工确认（completed） |

LLM 核验只在 L1 证据缺失时作补充判据。核验器版本冻结，并用人工盲标集测出精确率与召回率。每类约 100 条，可把估计误差控制在约 ±7 个百分点（计算见评测设计稿 §5）。

### 3.2 确定性步骤仍每步问模型（高）

- 主循环每步一次主模型调用。规划器与主模型是同一实例，每 3 步一次（`scripts/agent/service.py:618-628`）。场景摘要默认开，每 3 步一次。识图旁路默认开，用于高风险点击否决与 done 复核。合计约 1.7–2.2 次调用/步。
- 批量填表引擎 `run_form_assistant` 是完整的，但只在模型主动调用时触发（`scripts/controller/actions/_form.py:127`）。
- 录制期的确定性执行只有登录回放和进入功能页的菜单导航。跨菜单导航、查询选行、弹窗选人每次都重新探索。
- 失败默认重试 5 次、每次间隔 10 秒（`service.py:622`），与失败轨迹耗时长直接相关。

### 3.3 控件卡住：拒绝信息不可执行（高）

- 「同阶段重复操作」的拒绝以 **ok** 结果返回，附带的建议是「verify if needed and call done…」或「verify state and continue the phase」（`scripts/controller/actions/_form.py:85-91`，`scripts/controller/actions/click_action_engine.py:244-252`）。模型收到的是一个「成功」，下一步做什么并不确定。
- 重复失败纠偏只识别 `err-` 前缀（`scripts/controller/actions/result_protocol.py` 文件头的硬约束），所以这类伪装成 ok 的拒绝，即使打开 `AI_DUP_FAILURE_CUE` 也不会触发纠偏。该开关目前默认关闭（`scripts/feature_flags.py:241`）。
- 禁用字段、找不到元素、fill/select 互拒已经走三段式协议 `err-…|原因|现场|下一步`。剩余风险是控件类型判错时推荐了错误动作。

这三点合起来，是 9 月失败里「同阶段不许重复操作」9 条和长时间空转（例如轨迹 877 一个阶段 119 步）最可能的机制。修法很小：改为 `err-already-operated`，给出唯一下一步（换字段、`click_save` 或 `done`），并让纠偏识别它。

### 3.4 守卫层层叠加，复杂度在吞噬收益（中）

快照里与「能否完成」有关的门有十余道：零动作、零业务动作、未写完字段、缺成功令牌、口头声称无证据、弹窗未关、页面报错、识图拒 done、阶段末质量门、核验型豁免、引入完成、幂等点击与字段、空转守卫、重复失败纠偏、门禁提示行。成功令牌有三套来源（意图合约、边界合约 `success_when`、质量门 `missing_success_token`），未写完字段在 done 时和阶段末各判一次。相关代码集中在 `scripts/agent/recorder_emitters.py`（1505 行）、`intent_gates.py`、`boundary_gates.py`、`reviewer.py`，提示词里另有数十条规则。

部署版 09-30 已收敛为四道门，并给每次门判定留痕，方向正确。本报告不再建议重排守卫，只建议一条规则：**此后加门或改门，都要附评测数字。** `gate_decision` 已落库，可以按门统计「被拒后最终成功 / 失败」，得出每道门的误拒与漏拒。

### 3.5 资产沉淀了，但没有被复用（高）

| 环节 | 现状 | 断点 |
|---|---|---|
| 流程卡 → 录制 | 召回后把【流程卡模板】文本写进首阶段描述（`src/services/trajectory/trajectory-attach-runner.js:37-79`） | 只是文本提示，不驱动动作 |
| 卡的价值 | 覆盖率 M2 0.206、利用率 M3 0.321（57 张死卡）、新鲜度 M6 0.250；A/B 有卡 50% 对无卡 41.7%，差值在噪声内 | 收益集中在把多腿链路做完 |
| 录制 → 组件 | 挖掘接口按签名聚类出草稿，人工确认；`param_schema` 仍注释为「参数化预留」 | 没有「验证通过的阶段 → 组件」的钩子 |
| 组件 → 录制 | 只复用登录组件；`trajectory_phase.component_id` 预留且从不写入（`src/models/entities.js:132`，`src/services/operation-component-service.js:1-3`） | 非登录组件没有匹配、绑参、执行、接回状态机的通路 |
| 语料 → 组件 | 部署版已沉淀到草稿；按规格，草稿不参与召回 | 既定顺序是「召回（只注入提示）→ 复用」 |

判断：A/B 已经说明多给文本提示的边际很小。复用的价值在**执行**，不在**提示**。因此建议把既定的「先召回、再复用」调整为「白名单阶段直接复用执行，召回从简」。这改变了 09-24 交接文档里的排期，列为第八节待裁事项。

### 3.6 「录完」不等于「能用」（中）

- 录制结束只有零步门与质量门，不会自动回放验证。回放成功与否靠结果字符串前缀判断（`scripts/controller/actions/_replay.py:315-343`），失败原因没有统一枚举落库。
- 自愈决策开关 `HEAL_LOCATE_DECISION_ENABLED` 默认关，T3.1 真机验收未做。
- 信贷业务以写操作为主，回放写阶段会撞唯一键（例如「重复添加相同的证件号码」）。自动验证只能先覆盖导航、查询类阶段；写阶段需要参数化测试数据或人工。
- 定位短板集中在具体场景：树节点脏后缀、表格行只按首行定位、同名弹窗内外同文案。

### 3.7 平台：对外暴露与单进程调度（高）

## 四、方向比选

| 路线 | 做法 | 好处 | 代价与风险 |
|---|---|---|---|
| A 继续强化逐步决策的 Agent | 加门、加提示、换更强模型 | 改动局部，见效快 | 成功率上限约 80%；单步成本与时延不降；门越多越难改 |
| **B 首次探索，此后编译（推荐）** | 第一次由模型走通并验证；验证过的阶段变成带参数的确定性执行单元；录制先执行它，失败交回模型 | 命中的阶段从「每步十几秒」变成「整段秒级」；成功率随资产增长；与业界做法一致（Skyvern 按 block 缓存代码、Stagehand 缓存加自愈、SkillWeaver 只沉淀判定成功的尝试） | 依赖可信判定；页面漂移会误命中；写操作有脏数据风险。需要白名单、前后置条件和灰度 |
| C 人机协同优先 | 录中人工接管后交还、录制教练 | 成功率底线高 | 不降人工成本，偏离「自动产出可回放交易」 |

推荐 B 作主线：A 里的低成本修复放在第一阶段；C 的「录中接管」放在第三阶段作兜底（人工录制已存在，增量主要在状态机）。

B 内部还有一个次级选择：

| 选择 | 说明 | 结论 |
|---|---|---|
| 先召回（只注入提示），再复用执行 | 09-24 交接文档的既定顺序 | 提示类收益已被 A/B 证明很小 |
| **白名单阶段直接复用执行，召回从简（推荐）** | v1 只做跨菜单导航、查询并打开记录；默认 off，经 shadow 再到 on | 收益直接，风险由白名单和灰度控制 |

## 五、路线图

本节不估日历工期。「规模」按改动面描述：**小**＝单模块、无迁移；**中**＝跨 Node 与 Python，或含一次迁移；**大**＝调度内核或多模块联动。每个阶段有进入判据，不满足不进入下一阶段。

### 阶段 0：立即并行（安全 + 度量）

| 编号 | 内容 | 规模 | 验收 |

| S1 对外收口 | `SSO_AUTH_REQUIRED=true`；显式配置 `SSO_JWT_SECRET`，取不到验签密钥时拒绝，不再降级为不验签；`/v1/*` 校验代理令牌（执行机把 `LLM_API_KEY` 配成该令牌，执行机代码不用改）；配置 `DASHBOARD_WS_TOKEN`；health 不再返回目录；网络层只放行前端与执行机来源，`/ops`、`/api/docs` 走内网或令牌 | 小：以配置为主，`llm-proxy.js` 加一个中间件 | 外部匿名访问 `/api/v2/*`、`/v1/*`、`/ws` 均被拒；录制与执行机连接正常 |

## 六、不建议投入

| 项 | 理由 |
|---|---|
| 再扩召回算法（口语桥、同义词、向量检索） | 口语桥已失败关闭；召回对成功率的边际小于卡面正确性与执行复用 |
| 为覆盖率扩卡 | 覆盖回溯的结论是做准约 27 张活卡 |
| 只加强文本提示、不做执行复用 | A/B 中逐步遵循度两臂相当 |
| 加门或加规则而不附评测数字 | 见 3.4 |
| T3.1 之前默认打开 AI 自愈 | 没有真机证据 |
| 在挡板随机的账户弹窗上深挖定位 | 根因是被测系统挡板 |
| 把录制教练接进主循环 | 设计上是旁路，不降单步成本 |
| 多活控制面 | 先单活加租约落库，多活的收益抵不过复杂度 |
| 推翻子串 pin 体系 | 保留它对重构的保护，补行为层即可 |

## 七、主要风险与对策

| 风险 | 对策 |
|---|---|
| 页面漂移后误命中，走到错误状态 | 前置条件（页面键、可见元素）与后置条件确定性校验；连续失败自动挂起；菜单变更反查自动挂起 |
| 复用执行了写操作，弄脏被测数据 | v1 只允许不写库的阶段；确认时与每次运行前两次校验动作黑名单；每次复用的动作清单落库审计 |
| 评测样本量不够导致误判 | 轨迹级成功率只用于大效应决策；小效应看阶段级结果与连续指标（耗时、调用数）；配对设计 |
| LLM 核验误判污染指标与沉淀 | 成功分层；核验器校准与版本冻结；沉淀只认 L1 + L2 |
| 被测系统不稳定阻断验证 | 评测设「已知墙」对照任务；录前体检；失败原因分层统计 |
| 本报告依据的代码比现行代码早 5 周 | 设计稿列出「实现前复核清单」，在 js-project 核对插入点后再写实现计划 |

## 八、需要裁定的事项

1. 主线是否定为「首次探索，此后编译」（第四节路线 B）？
2. 是否把「召回提示 → 复用」的既定顺序改为「白名单阶段直接复用，召回从简」（3.5、第四节次级选择）？

5. 评测任务集由谁维护，占用哪台执行机和被测系统的哪个时段（评测设计稿 §3）？
