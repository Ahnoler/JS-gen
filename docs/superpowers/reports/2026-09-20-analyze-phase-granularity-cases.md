## 0. 文首总结：反复出现的合/拆理由（供 Cursor 抽规则）

1. **合段高频理由 A —— 确认弹窗并入触发它的动作**：analyze 常把「点【删除】」与「弹窗点【确定】」切成两段；人工一律合一（弹窗不是独立阶段，它是该动作的第二步）。
2. **合段高频理由 B —— 核验/重搜并入它要验证的变更**：「重搜确认节点消失」「重查确认状态已变」是**验证意图**而非独立阶段；独立成段会让阶段判据退化为"看页面"（#924 13→6、#877 8→7）。
3. **拆段高频理由 A —— 状态边界：展开动作必须与后续填写分段**：「点【更多】展开」改变的是**可操作字段集合**，与"填展开后的字段"分段（#861 7→8；#858 同类）。合并会让 agent 在未验证展开是否生效时去填不可见字段。
4. **拆段高频理由 B —— 相邻按钮 ≠ 同一语义**：「点【重置】」与「点【新增】」按钮相邻，但一个清查询条件、一个开弹窗，必须分段（#866 8→9）。
5. **拆段高频理由 C —— 触发页面跳转的提交必须独立成段**：弹窗内【保存】会跳到维护页，若与"跳转后的填写"同段，段内跨页导致判据无法界定（#866 把弹窗保存单列）。
6. **拆段高频理由 D —— 多同类控件逐字段各成段**：多条件下拉/输入逐字段分段，便于失败定位与证据归属（#858 把"三条件一段"拆成三段）。
7. **净段数不是判据**：同一条单里可以既拆又合（#858：拆 1 段为 3 + 合 2 段为 1，净 +1）——切点应是**「一个可验证的状态变更」**，不是按钮数、不是 UI 区域。
8. **现状量化**：27 条可比对轨迹中仅 **4 条**段数被人工调整（3 条 split、2 条 merge，#858 兼具）——**多数场景 analyze 粒度可直接接受**，人工干预集中在上述导航/核验类过度切分。
9. **后期干预已从"改粒度"转向"加门闩"**：#904 起我在 create 前做的主要工作变成给阶段描述补约束（提交按钮点名、落库核验、错位态重搜、导航复位配方、裁决前置声明）——**阶段描述的可执行性比段数更常成为卡点**，建议 checklist 同时覆盖"描述质量"一格。
10. **engine-workaround 不得沉淀为粒度铁律**（本报告 2 张卡）：同名/迁移字段跨阶段、跨对象清理拆段，都是**缺陷期规避**，对应缺陷已修复——请标 `no-workaround`。

## 6. 引擎线结论（2026-09-21，ZCode 引擎线）

**结论：不写「展开类瞬态动作必须独立成段」的动作类型硬规则，也不在 create 侧做自动拆分兜底。**

理由：

1. **与数据相悖的代价**：本报告 27 轨量化显示仅 4 条经人工调整，且主导偏差方向是**过碎**（#924 13→6、#877 8→7、#866 8→9 中的合并侧），提示词 Rule 9 已明写「能少则少，能合并就合并」。新增动作类型级「必须独立成段」规则会与主导偏差叠加，把代价从"少一个观测面"换成"多段数 + 多步数预算"——而步数预算恰是稀缺资源（B 类报告 §一 自身即以此为立论）。
2. **判据已在提示词内**：现有 Rule 3 / 3.1 已确立**状态边界原则**（「阶段边界必须落在稳定、可判定的页面状态上」）。"展开改变了可操作字段集合"正是该原则的一个实例，无需引入新的动作类型维度。
3. **自动拆分兜底不做的理由**：拆点判定依赖"哪些后续动作依赖展开后才可见的字段"这一业务语义，机械不可判；误拆直接增加段数与步数。人工调整成本（4/27）显著低于误拆的期望成本。
4. **采纳贵线建议的正确内核（方向修正）**：把「展开类」从**粒度问题**移到**可执行性问题**——干预走**门闩**而非改粒度：在阶段描述里点名"展开后需确认字段集已出现再填"的判据（与贵线 §0.9「后期干预已从改粒度转向加门闩」同向）。

**可随时启用的候选措辞（备查，未落库）**：若该族（展开并入填写 → 观测面缺失）在门闩化之后仍复现，可在 Rule 3 增一句判据式弱提示：

> 3.2 若某阶段内先有「展开/切换页签」等改变可操作字段集合的瞬态动作、且其后紧接对这些新出现字段的填写或判据，宜在此切开（与 3.1 状态边界原则同源）。

启用需一次 wet 观察（改提示词会动 analyze 输出，离线不可验），故本轮不落库。
