## B 类：引擎/录制执行链缺陷（移交录制执行线）

### B-1 TsscMultiSelect 字段 fill/select_option 路由互拒
- **现象**：评级申请向导「风险阻断」抽屉内的 TsscMultiSelect（下拉多选）字段，`fill_form_field` 与 `select_option` 互相拒绝路由：fill 报「请用 select_option」、select_option 报「请用 fill」，agent 在两动作间震荡 7 步不收敛（traj #864，executor-main.log L830-865）；换会话后同字段 tssc 路由一次成功（#865）。
- **影响**：非致命但严重浪费步数（预算 300 步内可被震荡耗尽），成功率取决于路由判定顺序。
- **复现**：评级申请向导页 → 风险阻断步骤的多选字段（如「业务往来及使用」族）。参考 traj #864 步日志。
- **线索 file:line**：fill/select 路由判定在 `scripts/controller/actions/fill_dispatch.py` / `select_dispatch.py` 的 tssc 分支；建议在 tssc-multi-select 容器识别后固定单一动作提示，或将两动作对该控件类型收敛为互认。
- **建议优先级**：P1。

### B-2 trajectory_step 行数与 stepCount 不一致（疑 coalesce 吞并行）
- **现象**：traj #859 API stepCount=13，DB `trajectory_step` 实际 15 行；#858 P4 曾现 stepNumber 8 空号。疑 recording coalesce（`scripts/state.py _record_action`）保留被并并行时行删除/计数的口径不一致。
- **影响**：以 stepCount 驱动的对账/导出会低估实际落库步数。
- **线索**：`scripts/state.py` `_record_action`（coalesce 发 emitted removedIds 时）与 step 持久化计数的对账。
- **建议优先级**：P2（观察项，先加对账日志确认根因再修）。

### B-3 executor 僵死双进程（同 uuid 半开重连）
- **现象**：湿测三开工前发现 LMY 执行机有两个相同 nodeUuid 的 executor 进程，均处于半开重连循环；控制面注册一真一假（DB 留 offline 旧注册）。手工杀双进程后单实例重启恢复。
- **影响**：槽位状态错乱、心跳互踩；录制中会话不受影响但后续调度可能选中僵死实例。
- **复现/线索**：executor 重启时未做同 uuid 旧进程互斥/退避自杀；`executor/agent.mjs` 重连逻辑（unref 修复 606277a 之后的场景）。
- **建议优先级**：P2。

### B-4 MySQL deadlock 死锁重试自愈（观察项）
- **现象**：server-main.log L2070 步持久化遇 MySQL deadlock，重试后自愈成功（traj #863 录制期间）。
- **影响**：暂无损失；高频并发录制时可能升级为可见失败。
- **建议优先级**：P3，记录观察即可。

### B-5 analyze 阶段合并摩擦（管线体验，非缺陷）
- **现象**：analyze 对「点击【更多】展开」「返回+查询」等常输出合并阶段（如展开并入填+查），与任务分阶段设计不一致，create 时须手工拆回（#861、#866 两轮均手工调整）。
- **影响**：每次录制多一步人工对齐；不修不影响正确性。
- **建议优先级**：P3。

## C 类：SUT 与需求基板差异（移交 SUT/需求确认侧，录制任务设计已绕行）

### C-1 客户状态默认值与文案不符
- **需求**：新增对公客户向导「客户状态默认显示为潜在客户」（A02 §向导页）。
- **实际**：默认「信贷预客户」，向导内不可改；保存后列表显示「草稿客户」（traj #859 doneLogs 如实记录）。
- **建议**：需求基板或 SUT 二者取一修订；录制任务文案已按实际值写。

### C-2 评级客户选择器只列「信贷正式客户」+ 具名正式客户池耗尽
- **需求**：选择客户范围=客户状态为「信贷正式客户」的对公客户（B01 §选择客户及模板 L166/L185）。
- **影响**：湿测新建的草稿客户进不了评级选择器。当前系统内可用正式客户（瑞云智联科技有限公司、贯通验证企业190416有限公司）均已因在途评级流程不可再发起——**后续评级/授信类测试前须先做客户转正补充正式客户**。
- **在途拦截规则实证**：「该客户已发起评级流程，请等待流程完成后再进行评级」（#864/#865 正确负路径）。

### C-3 客户名称查询条件实为「引入」弹窗形态
- **现象**：评级申请主页（ZJJK00070599）的「客户名称」查询条件不是直接输入框，点击后弹【引入】选择器回填；录制 agent 按直填预期操作会自判「未完成」（#863 P3 落库 7 步含 query_clicked 证据但诚实自报失败→整轨 failed 闩存）。
- **建议**：评级类任务文案按实际形态写「点击客户名称条件→在引入弹窗中搜索选择」（已验证可行）；**不新增专用动作**——引擎动作词表冻结（六 type 支撑 18 操作），如需降低摩擦走现有动作内的提示词 cue 强化（`scripts/prompts/**`，与 js_snippets cues 同步约束）。

### C-4 个人客户新增基本信息页三道 SUT 硬依赖（#867/#868 阻断点）
1. **配偶三件套必填且「引入」不能选本人**：基本信息页（viewType=add）要求配偶证件号码/客户编号/姓名必填，引入选择器拒绝「当前客户和所选配偶不能为同一个人」——需要预置一个配偶客户才能走通（数据依赖，测试设计须两步：先建配偶再建本人）。
2. **「联网核查结果」disabled**：下拉不可直接选，须点【联网核查】按钮发起核查后回填——与湿测任务「禁入核查按钮」冲突，任务设计需放开该按钮或接受此环节跳过。
3. **该页无【返回】按钮**：viewType=add 页面不存在返回按钮（#868 P7 落空），任务应改「取消/菜单导航返回」。
- **建议**：①③属任务口径可绕；②需 SUT 侧确认「联网核查」是必经环节还是可后补（需求 A02 §维护个人客户基本信息 未写明 disabled+强依赖关系）。

### C-5 需求基板枚举缺项
- **现象**：个人客户新增弹窗「对私客户类型」需求取值「自然人」在 SUT 下拉中不存在（实际为「其他自然人」等）；对公「客户名称」选择器搜索按键与需求描述亦有出入。
