# 录制效率与成功率：下一步开发方向（2026-09-24）

> 只读调研，未改产品代码。五路并行：失败与耗时实证（只读查库）、录制 Agent 主循环、知识与资产复用、录制产物回放与自愈、2025–2026 业界做法。
> 建议顺序见文末。本文是方向报告，不是实现规格。

## 一、结论

近 45 天 AI 录制成功率约 **71%**（292 条里成功 208 条），最近两周约 **61%**。失败轨迹的活跃录制时间中位 **7.6 分钟**，成功轨迹只有 **2 分钟**。

本产品能修的失败里，最大一块是**控件操作卡住**（约 30% 的失败），其次是**阶段完成判定误判**（约 10%）。被测系统自身拒绝或报错约占失败的 20%，根因不在本产品，但可以在录前拦住、少白跑。

提速的主线是：**已经验证过的步骤不要再每步问一次模型**。批量填写一步不到 1 秒；需要模型决策的点击，中位 15–36 秒。现在录制期会回放已有组件的，只有登录。

建议先做三件小改动：控件拒绝时给出唯一可行提示、打开两个已写好但默认关闭的开关并湿测、把失败原因落库。这三件同时提高成功率，并给后面的提速和自动沉淀提供度量。

## 二、数据基线

只读查询 `47.101.58.49:3306`，窗口为 `updated_at` 近 45 天。AI 轨迹指含 agent 步骤的，共 330 条，排除草稿后 292 条。另有 237 条纯人工 CDP 录制未计入。

### 失败构成（84 条失败）

同一条轨迹可能命中多类，占比是估计。44 条发生在 09-18 之前，当时还没有失败原因列。步骤表的 error 列是 0 行、success 列全空，原因只能从阶段结束日志的关键词推断。62 条失败轨迹的所有阶段都是 completed，也就是 agent 自己报了失败——这里面被测系统拦截和合约误判混在一起，数据分不开。

| 失败类别 | 约占比 | 代表轨迹 | 本产品能否修 |

第 1、2 类（控件卡住 + 合约误判）合计约 35–40 条，占全部录制的 12–13%。两类都修掉，成功率上限大约到 80% 出头。实证子报告里「控件卡住可提高 10–15 个百分点」偏高：该类只有 25–30 条，全修掉最多约 10 个百分点。

## 三、五个方向

### 1. 先治控件卡住

这是本产品能修的最大一块失败。高频情形是禁用字段、同阶段不许重复操作、找不到元素、fill 与 select 互相拒绝，并常伴随空转（轨迹 877 的一个阶段耗了 119 步）。

近期：

- 碰到这几种拒绝时，把唯一可行的动作写进下一步提示。
- 两个开关已实现、默认关闭，湿测后打开：重复失败纠偏 `AI_DUP_FAILURE_CUE`（`scripts/feature_flags.py`，默认 false）；被测系统空转守卫 `SUT_SPIN_GUARD_MODE`（`scripts/agent/recorder_emitters.py`，默认 off，todo `recording-redundant-step` D2 已合入）。

长期：把树选节点、表格行、级联、弹窗「查询—选行—确定」做成带参数的多步技能。业界对照：WALT（ICLR 2026）真实网站成功率 42.9%→51.2%、步数 10.8→8.2；WebXSkill（arXiv 2604.13318，2026-04）在 WebArena、WebVoyager 上最多提高 9.8、12.9 个百分点。本仓已有控件级片段和文本流程卡，缺的是多步参数化技能和按页面状态检索。

### 2. 阶段完成判定改为看证据

近期三件已经点名、改动小：

- legacy 令牌别名表（A/B 报告里 744 被质量门误杀）。
- 核验型阶段主收口：todo `verify-phase-token` 的第一步门侧兜底已合入，第二步（`apply_phase_contract` 同笔清掉 `success_when`）等湿测零误报后再做。阳性例是轨迹 973，对照是 924。
- 仅导航的阶段豁免零步检查（733/741/742 被误伤）。

再往前：done 判定按证据逐条核对（接口成功、toast、弹窗关闭、列表出现新行），不采信模型自述。逐步反馈已经在采这些信号。业界对照：WebJudge（arXiv 2504.01382）不把 agent 的最终回答交给判官，与人工一致率 85.7%；Universal Verifier（arXiv 2604.06240，2026-04）把过程与结果拆开打分，误报从 30%+ 降到 1–8%，收益来自评判结构而不是换更强的模型。browser-use 文档也写明 `is_successful` 只是 agent 自报。

可靠的判定是后面「缓存回写」和「经验自动入库」的前提。不建议关掉 Phase Reviewer：步数预算依赖它产出的合约。

### 3. 确定性步骤不再每步问模型

这是提速主线。成本结构（录制 Agent 主循环）：

- 每步 1 次主模型（`scripts/agent/service.py` 构造 Agent 处）。规划器与主模型同一实例，`planner_interval=3`，每 3 步再加一轮。场景摘要 `AI_SCENARIO_DESCRIBER` 默认开，同样每 3 步一次。长阶段 30 步大约多 10–20 次调用，和主步看到的内容高度重叠。
- 识图旁路 `AI_RECORD_VISION` 默认开，用于 done 复核和高风险点击否决。不建议一刀切关掉；应保留，并继续用已落地的识图专用模型配置。
- `wait_for_loading` 遮罩轮询最多 30 秒。重复失败默认 `max_failures=5`、`retry_delay=10` 秒，纠偏提示却默认关。
- 表单批量填写（`run_form_assistant`）引擎是齐的，但要靠模型自己调用。填写类阶段若开头按合约自动填，主模型往往只需处理树、引入、保存。交接文档里的量级是一个大表单阶段从大约 10 步降到 2–4 步。

复用现状：录制期回放已有组件的只有登录（`src/services/trajectory/trajectory-record-lifecycle.js` 查找 auth 组件）。菜单导航、查询选行、弹窗选人每次重新探索。`record/start` 已支持 `phaseIds` 只录指定阶段，没有「从失败阶段续录」的产品路径。`trajectory_phase.component_id` 仍是预留字段。

业界做法是第一次让模型探索，之后按阶段回放缓存或生成的代码，失败再交回模型：Skyvern 按 block 缓存代码；Stagehand 的 `cacheDir` 加 `selfHeal`；workflow-use 自称比逐步 agent 快约 10 倍（作者在 HN 上的数字，2025-05，未独立核实）。本仓已有回放引擎和阶段合约，缺的是录制期按阶段去命中它们。

知识库侧：对已命中的录制，卡面是否正确比召回再抬几个点更要紧。覆盖回溯（2026-09-11）M2 覆盖率 0.206、M3 利用率 0.321（57 张死卡）、M6 新鲜度 0.250。A/B（各 12 次）有卡 50% 对无卡 41.7%，差值落在噪声里；有卡的优势是把多腿链路做完，不是逐步更贴卡。生产召回 Acc@1 0.74 对绑卡够用。

### 4. 失败早发现，不从头重来

- 先把失败原因和步骤级页面错误落库（todo `record-page-errors`）。现在约一半失败没有原因码，第 1–3 项做完也量不准。
- 录前体检：在途流程、正式客户池、角色是否绑用户。这约 20% 的失败本产品根治不了，但可以不启动录制。
- 执行机 / 运行时异常 9 条（`runner_error`、中断）单独查。
- 失败后续录：API 有 `phaseIds`，缺产品上的「从失败阶段接着录」。阶段内失败现在是整轨失败，预算延长最多 2 轮。
- 人机协同：AI 录制进行中，人工录制返回 409（`src/services/trajectory/trajectory-manual-record.js`）。可以对连续失败开放录中接管，人工步骤落库后交还。Magentic-UI（微软研究院，2025）在模拟用户提供人工计划时，完成率 30.3%→51.9%，且只有约 10% 的任务求助。Recording Coach 设计稿已定、未实现；它不进主循环，不解决单步成本。

### 5. 录完即验证，验证过的经验再沉淀

- 录制结束只有异步终局门闩（零步或 `quality_failed`），不会自动 `steps/replay`。可以在录完对关键阶段做一次短回放，把「能回放」算进验收。批回放和登录回放链已经有了。风险是占用执行机、弄脏被测数据。
- 探索点击、失败重试、非连续的重复填写仍会落库。终局可以标出或删掉这些步，而不是录制时硬砍（硬砍会丢掉排障信息）。同参数重复步约占 9%。
- 回放自愈：Type A 单步、Type B 表单结构增删已有代码和 pin；`HEAL_LOCATE_DECISION_ENABLED` 默认关；T3.1 真机验收还没做。先做 live 验收，再谈默认打开。回放失败目前不会回写流程卡，也不会触发重录某一阶段。
- 沉淀：主链那 11 条实证规则是会话里人工写入 `data/kb/flows/*.json` 的。自动链路只到 `_append_kb_staging` 写 JSONL，再由 `scripts/kb/promote.py` 人工 `--apply`。验证通过后再生成规则或组件草稿，人工发布。SkillWeaver（arXiv 2504.07079）只把判定成功的尝试写入技能库。组件挖掘接口 `POST /api/v2/operation-components/mine` 已有；todo ⑧′「已确认交易扫描 → 原子组件」明确不在本版。

定位短板留在场景上，不重做 select/fill/radio/click 的录放架构：树节点兜底（todo T1r）、表格行语义键、同名弹窗内外同文案（page-state-wet 未湿测）。合同账户弹窗候选随机是被测系统挡板，定位再强也不稳。

## 四、不建议投入

| 项 | 理由 |
|---|---|
| 口语桥、同义词表接线、embedding 混合检索 | 口语桥已关闭（评测集 E 层 Acc@1 0.100，开关前后逐位相同）。召回对录制成功率的边际小于卡面正确性 |
| 为覆盖率扩流程卡数量 | 覆盖回溯的结论是把约 27 张活卡做准，并按真实频次补缺口 |
| 只加强流程卡文案注入、不做步骤复用 | A/B 里逐步遵循度两臂差不多；多腿收益来自链路提示，不来自排序 |
| 关掉 Phase Reviewer，或默认关掉识图旁路 | 步数预算依赖合约；图标和引入点击会掉成功率 |
| 重做四类控件的录放统一，或做非 el-table 自定义网格（T5） | 架构已统一；T5 缺页面证据，todo 标为暂缓 |
| 在挡板随机账户弹窗上深挖定位 | 根因在被测系统 mock |
| 默认全开 AI 自愈代替确定性回放 | 先做 T3.1 live 验收 |
| 录制时禁止失败步落库 | 丢掉排障信息；放到终局校验 |
| 把 Recording Coach 接进 Agent 主循环 | 设计上就是旁路，不降低单步成本 |

## 五、建议顺序

1. **先做**：方向 1 的近期部分（拒绝提示 + 两个默认关的开关湿测后打开）、方向 2 的近期三件、方向 4 的失败原因落库。改动小，并且让后面的项可度量。
2. **提速主线**：方向 3。填写阶段自动批量填表，再把登录组件的回放做法推广到菜单、查询选行、选人；规划器和场景摘要降频或换小模型。
3. **放后面**：方向 5 的自动沉淀。前提是方向 2 的判定先可靠，否则会把误判写进知识库。组件库产品化沿用 todo ⑧′，不进本版实现。
