# Atom 拆分样例：`produces` / `dataDependsOn`

这些例子说明**依赖图**怎么切 atom。它们碰巧来自产品库湿测（#675 / #676 / #678 / #504），**不是**「树的每一层必须拆」教条。换到客户、合同或其它对象，规则相同：后一步要新建/修改的对象依赖前一步 `produces` 的键，就必须拆成两笔，用 `dataDependsOn` 串联。

## 正例：三条独立可录交易

| atom | 对齐湿测 | produces | dataDependsOn |
|------|----------|----------|---------------|
| A | #675 新增一级 | `["一级分类"]` | `[]` |
| B | #676 新增子分类 | `["子分类"]` | `["一级分类"]` |
| C | #678 新增产品 | `["产品"]` | `["一级分类", "子分类"]` |

前置草稿完成后，每一笔都应能**单独开录跑通**。B/C 只搜索/展开/选中**已存在**的依赖对象，再做本笔一次落库；不在本笔里新建上游。

### A · 对齐 #675

本笔新确立一级分类；无上游数据依赖。

```
produces: ["一级分类"]
dataDependsOn: []

taskDraft:
1、进入功能页，等待加载
2、打开新建入口，填写名称/序号等字段
3、【确定】保存成功

关键数据
一级分类：KB测一级
```

### B · 对齐 #676

本笔新确立子分类；开录前一级分类须已存在（来自 A，或 `source: "preset"`）。

```
produces: ["子分类"]
dataDependsOn: ["一级分类"]

taskDraft:
1、进入功能页，等待加载
2、搜索/定位并选中已有「一级分类」
3、打开新建子级入口，填写字段
4、【确定】保存成功

关键数据
一级分类：KB测一级
子分类：KB测子类
```

### C · 对齐 #678

本笔新确立产品；开录前一级、子分类均须已存在。

```
produces: ["产品"]
dataDependsOn: ["一级分类", "子分类"]

taskDraft:
1、进入功能页，等待加载
2、搜索/展开并选中已有「一级分类」「子分类」
3、打开新建产品入口，填写字段
4、【确定】保存成功

关键数据
一级分类：KB测一级
子分类：KB测子类
产品：KB测产品
```

`dataDependsOn` 也允许对象形式，例如 `{ "key": "一级分类", "source": "preset" }`（预置数据，不要求同批其它 atom `produces`）。

## 反例：#504 本笔造上游 + 自产自依赖

把「造一级 + 造依赖一级的子类/产品」合成一笔，或在 `taskDraft` 写「若找不到父节点则先新建父再继续」，都违反拆分边界。

```
# 不要这样
produces: ["一级分类", "子分类", "产品"]
dataDependsOn: ["一级分类", "子分类"]   // 与 produces 相交 → 自产自依赖

taskDraft:
1、进入功能页
2、若找不到父级则先点【新增一级分类】造父
3、再新增子分类 / 产品并【确定】
```

问题：

1. `produces ∩ dataDependsOn` 非空 → 硬拒 `self_produce_depend`。
2. 「找不到上游则本笔先造上游」是 #504 式兜底：缺上游应拆出上游 atom，或标 `source: "preset"` 并由人保证预置。
3. 湿测 #504 还因按钮口径错误造出幽灵顶层；拆笔 + 先搜索再写可避免把兜底写进同一交易。

正确做法仍是上面的 A → B → C 三条链，而不是「凡树必按层拆」的场景清单。

## 能力内聚：一笔草稿一项业务能力

依赖图回答「谁必须先于谁落库」。**能力内聚**回答「同页、同段落里哪些步骤属于同一项可独立验证的业务能力」。两者同时遵守；不要把具体按钮文案或对象层级写成拆合清单。

直觉（仅说明形态，不是场景法）：维护已有对象可以是「搜索/选中 → 打开表单 → 改该能力字段 → 一次保存」为**一项**能力（湿测维护形态如 #708）。列表上另一次可独立验收的操作（如核对排序结果）与详情保存是**不同**能力，须各成 atom。新建互相依赖的对象（如 L1 / 子级 / 产品）仍由 `produces` / `dataDependsOn` 拆开。

### 正例：定位 → 填写 → 一次落库（同一能力）

搜索/选中已有对象、打开表单、填写**该项能力**的字段、一次落库——准备步骤服务于这一项能力，不是另一项能力。

```
produces: ["已维护对象"]
dataDependsOn: ["已有对象"]

taskDraft:
1、进入功能页，等待加载
2、搜索/定位并选中已有对象
3、打开该项能力对应的表单或页签，填写本能力字段
4、一次【保存】成功

关键数据
已有对象：KB测对象
已维护对象：KB测对象
```

### 反例：同页多能力合写

不要因为两项能力出现在同一页面、同一需求段落、甚至同一对象上，就把它们写进同一 `taskDraft`。

```
# 不要这样
produces: ["已维护对象"]
dataDependsOn: ["已有对象"]

taskDraft:
1、进入功能页
2、在列表上做一项可独立验收的操作（例如调整顺序并核对其结果）
3、再选中同一对象，打开详情，改另一组字段并【保存】
```

问题：

1. 列表上那项可独立验收的操作，与详情里的保存，是两项能力；同页、同对象不能当成合并理由。
2. 准备步骤只允许服务本笔能力（定位 / 打开 / 填本能力字段），不能顺带做另一项可单独开录的能力。
3. 正确：各成一笔 atom。维护笔只含定位 → 填本能力字段 → 一次保存；另一项可独立验证的能力（若需保留）单独成 atom。

这与「禁止按场景清单强制拆笔」不矛盾：判断标准是「能否独立验证 / 独立开录」，不是某几个按钮词或树的层数。
