## 6. 远程 DB 性能与稳健性热修（H1-H3，全部已落地）

**背景（实锤数据）**：8-28 本地控制面切远程库（47.101.58.49）后，单程 RTT 38-92ms（均值 ~65ms）；录制台刷新突发 + 10s 全量树轮询把连接池打满（max=10 / acquireTimeout=10s），`Knex: Timeout acquiring a connection` 间歇爆发。两个实测后果：① prepare 的 DB 步骤撞超时 → HTTP 500 → 前端停在错误态、画布"断流"（后端流实际 attached，`live/status` 可证）；② `recording-page-bind.js` 的 `updateMeta` 被外层 catch 静默吞掉 → 轨迹 33 的 pageId 停留 AILZ 兜底值。

三项热修集中在 **`b0a78d8`**：

- **H1 池扩容**：`config/.env` `DB_POOL_MAX=20`（MySQL max_connections=200，余量充足；`.env.example` 留注释模板）。SSH 隧道选项不降 RTT（同一公网路径），收益是收敛 3306 暴露面。
- **H2 page-bind 加固**：① 同菜单复用守卫——导航返回 `same-menu` 且 `runtime._pageBoundId` 已有值 → 复用返回 `reused:true`（顺带消除每次进录制台重弹天元弹窗）；② `updateMeta` 失败不再静默——单独 try/catch、warn 带 `PERSIST-FAILED` 标志、返回值增 `persisted:false`。均在 `src/services/trajectory/recording-page-bind.js` 现码可查。
- **H3 传输压缩**：`config/database.js` 开 `compress: true`（mysql2 压缩协议）——431KB 重复性 JSON 载荷实测 465~914ms → **~105ms（4~9×）**，全部查询受益、零接口形状变化；slim 否决理由见 §2。

**H4 操作纪律（长期有效，不改代码）**：录制台刷新后等 prepare 走完再操作，不要连续刷新——刷新本身即负载洪峰。前端轮询降频属 vue 仓库。
