## 8. 2026-08-31 湿测新增——远程 DB 性能与稳健性（H1/H2 热修优先于波次）

**背景（实锤数据）**：8-28 本地控制面切远程库（47.101.58.49）后，实测单程 RTT 38-92ms（均值 ~65ms）；
录制台刷新突发 + 10s 全量树轮询把连接池打满（`config/database.js` max=10 / acquireTimeout=10s），
`Knex: Timeout acquiring a connection` 间歇爆发。两个实测后果：
① prepare 的 DB 步骤撞超时 → HTTP 500 → 前端停在错误态，画布"断流"（后端流实际 attached，`live/status` 可证）；
② `recording-page-bind.js` 的 `updateMeta` 被外层 catch 静默吞掉 → 轨迹 33 的 pageId 停留 8-27 的 AILZ
兜底值（当日 5 次 read 均成功读得 ZJJK00066153 但未落库）——起点页面 ID 绑定实际失效。

### H1（热修·配置，立即）DB_POOL_MAX
- `config/.env` 增 `DB_POOL_MAX=20`（MySQL max_connections=200，余量充足）；改后重启 server→executor（顺序固定）
- 若改走 SSH 隧道（`config/open-db-tunnel.cmd`，127.0.0.1:13306→49 机 3306）：RTT 不会降低（同一公网路径，实测 ~65ms 量级不变），
  池扩容仍必要；隧道好处是 3306 不再对公网暴露 + 凭据不走过明文端口，`.env` 相应改 DB_HOST/DB_PORT

### H2（热修·功能正确性，立即）recording-page-bind 加固
