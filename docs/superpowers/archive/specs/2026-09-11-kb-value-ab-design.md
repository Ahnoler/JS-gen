# KB 价值 A/B（方向 2）— 设计

> 日期：2026-09-11 · 作者：DSH reviewer（Lead 委托）
> 上游：方向 5 收口（[`2026-09-11-direction5-r3-go-nogo.md`](../reports/2026-09-11-direction5-r3-go-nogo.md)）· 覆盖回溯（[`2026-09-11-kb-coverage-retro.md`](../reports/2026-09-11-kb-coverage-retro.md)，判决 [`…-g-verdict.md`](../reports/2026-09-11-kb-coverage-g-verdict.md)）
> **一句话：把"KB 到底有没有用"变成一个可跑、可收数、可复核的对照实验——同一条需求跑两臂（无提示 / 有流程卡提示），比成功率与成本。这是 KB 立项以来第一次测"价值"，此前只测过"资产质量"与"召回准确"。**

## 1. 问题与假设

- **H1**：在需求→录制这条真实链路上，**注入流程卡提示（【流程卡模板】）能提高录制成功率 / 降低步数与人工介入**。
- **H0**：提示内容对结果无影响（差异来自噪声/运行顺序）。
- **不测**：召回准不准（v2 评测集已测）、卡内容对不对（覆盖回溯已测）。**本线把"卡"当既定输入，只测"给 agent 看卡"这件事的价值。**

## 2. 实验设计

| 项 | 设计 |
|---|---|
| 实验单元 | 一条**需求文本** → 一次录制交易（一个 `trajectory`） |
| 需求集 | 来自 `batch_recording_item.requirement` 的**去重 36 条**（用户/QA 手写、产品语体），经 T0 筛选成 12 条可跑需求 |
| A 臂（对照） | 现管线原样：phase description = 需求分析产出的原文 |
| B 臂（处理） | **同一条 phase description**，仅在其前加 `buildFlowTemplateHint(card)` 的【流程卡模板】块 |
| 自变量纯度 | 卡的选取由 **冻结映射（需求→卡）** 给定，**不由召回决定**——否则会把"召回对不对"混进来。B 臂的卡由 T1 离线人工确定并冻结 |
| 可选 C 臂（仅 pilot） | 提示块换成**邻域错误卡**（同模块另一张卡），做"特异性对照"：若 C ≈ B，则收益来自"任何额外文本"而非 KB 内容 |
| 配对 | 每条需求在 A/B 两臂各跑一次，**同一账号、同一时间窗内成对先后跑**（控制环境漂移） |
| 顺序 | 每条需求的臂顺序**交替**（A→B、B→A），避免顺序效应 |
| 规模 | **pilot 2 需求 × 2 臂（+C 2 条）** → 验管线与基线天花板；**正式 12 需求 × 2 臂 = 24 次录制** |
| 一次机会 | 每次录制只给一次机会；失败即记失败，**不自动重试**（重试另记 run，标 `retryOf`） |

## 3. 观测量（全部从库里按 trajectory id 收，确定性）

| # | 量 | 来源 | 角色 |
|---|---|---|---|
| P1 | **成功率** | `trajectory.record_status ∈ {recorded, completed}` / `is_successful` | **主判据** |
| P2 | 成本 | `step_count`、`phase_count`、墙钟（`created_at`→`updated_at`） | 解释项 |
| P3 | 人工介入 | `trajectory_step.source='manual'` 步数占比 | 解释项 |
| P4 | 返工 | `trajectory_step.error` 非空步数 | 解释项 |
| P5 | **卡片遵循度** | 实跑 `visitedRegions[].key`（`page_level_key`）与卡 `hash_markers` 路由；`click_button` 文案与卡 `nodes[].buttons` 命中率 | 机制证据 |
| P6 | 越界 | 卡上不存在的页面 / 写操作黑名单按钮命中数 | 安全项 |
| 统计 | 每臂成功率 + 差值 + **Wilson 95% CI**；n 小只作方向性结论，不宣称显著性 | — | 口径 |

**先验功效提醒（写进报告，不许事后找补）**：n=12/臂时，只能可靠检出 ≥30pp 的差异；20pp 级差异需要 n≥40/臂。**因此正式线只接受"大效应"结论；小效应一律记为"证据不足"。**

## 4. 天花板检查（T0 硬前置）

若 pilot 里 A 臂成功率 ≥ 0.9，则该需求集**无信息量**（不可能显示改善）→ 必须换难度锚：改用**历史上真实失败且非基础设施原因**的需求族（已识别的候选：新增客户 stamp 族 #586/#590/#592/#593/#594，对公用信 #615）。**不得**把 wet-test/noop/引擎跑批类失败（#721/#720/#429/#210…）当作难度证据。

## 5. 环境、隔离与清理（硬约束）

- 环境：本地控制面 `npm start`（4097）+ executor + Chrome；SUT `http://test.creditv5p2.tansun.com.cn`；LLM 网关已实测可达（778ms）。**单条串行**，不并发。
- **SUT 是共享测试环境**：所有写入数据带前缀 `KBAB<runId>-`；只做可回滚操作；跑完按清单清理并留证（清理结果写进 manifest）。
- **不碰他人数据**：库里已有的 `KB测…` 遗留一律不动。
- 账号：固定一个专用测试账号，记录在 manifest（不写口令）。
- 失败/超时不重试（§2）；异常中断的 run 标 `aborted` 并排除出统计（同时记录，不许静默丢）。

## 6. 交付物

| 交付 | 路径 |
|---|---|
| 冻结 manifest | `scripts/kb/kb-ab-manifest.v1.json`（需求文本、需求→卡映射、臂分配、顺序、账号、前缀、清理清单、`frozenAt`） |
| 收数引擎 | `scripts/kb/kb-ab-eval.mjs`（按 manifest 里的 trajectory id 从库收 P1–P6；`--json`；确定性） |
| 协议门禁 | `scripts/characterization/characterize-kb-ab.mjs`（形状/配对/臂平衡/无跨臂污染/收数完备；**不设成功率 floor**） |
| 报告 | `docs/superpowers/reports/2026-09-11-kb-ab-*.md`（pilot 与正式各一份） |

**门禁为什么不设成功率 floor**：成功率是统计量，n 小会抖；把它做成硬门会变成"flaky 门禁"，进而诱发调参凑数。门禁只保证**协议与数据完整性**；结论由报告 + CI 承担。

## 7. 反作弊 / 口径守则

1. **不许按结果挑样本**（剔除失败 run 必须走 `aborted` 白名单理由，且全部记录在案）；
2. **不许事后改臂定义**（臂定义与卡映射在 T1 冻结，改动 = 新版本 manifest）；
3. **不许用 v2 评测集的需求**（那是召回评测资产，物理隔离）；
4. **不许把 C 臂结果混进 A/B 主表**；
5. 报告必须给出**原始逐 run 表**（id、臂、需求、结果、步数），不是只给汇总。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 成功率天花板（A≈1.0） | T0 pilot 先测；触顶则换难度锚（§4） |
| SUT 共享环境污染 | 前缀 + 只可回滚操作 + 清理留证 |
| LLM 非确定性 | 成对、同窗、交替顺序；报告附 run 时间戳 |
| 样本小 | Wilson CI + 只接受大效应（§3） |
| 录制耗时长 | pilot 先跑；正式线分批，报告按批记录 |
| 与在途线冲突 | 本线只新增 `scripts/kb/` 文件与报告；**不碰 `src/**`**（提示块由 prepare 既有机制产出，本线不改代码） |
