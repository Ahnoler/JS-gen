# B 级立项真伪需求审查（2026-09-05）

> 审查对象：`2026-09-05-partner-exchange-research.md` 提出的 B 级四项（B1 定时触发 / B2 KB 业务分层标签 / B3 缺陷单关联 / B4 晋升工作台）。
> 审查动机：用户质询「是否是项目的真实需求，是否是伪需求」。审查判据三条：①**消费者判据**——具体谁用、用多频，答不出=伪；②**定位判据**——本仓是「录制/回放工具 + 信贷 KB」，不是「测试执行平台」，能力清单是否属于别的产品形态；③**替代判据**——现有能力是否已闭环痛点。
> 结论先行：**B 级四项按当前证据全部不具备立项条件**。其中 B1 原命题与 B3 属产品形态错配，B2/B4 属无消费者/无痛点。各留一个「重新表述后的种子」进观察名单，触发条件明确后再议。

## B1 批量定时触发 → 原命题为伪；重新表述为「KB/菜单漂移定时巡检」

- **原命题批判**：定时触发**录制批量**不成立——录制是一次性资产生产（录完即有），不存在"每天录一遍同样交易"的场景。伙伴的「定时执行」是测试执行平台语义（定时跑用例集做回归），其前提是拥有用例集执行器；本仓的批量是录制批量，语义错配。
- **本仓的真实等价物**：没有。这是定位差异，不是能力缺口。
- **种子（观察名单）**：「定时巡检」的真实版本是 **KB 卡漂移 + 菜单变更巡检**——`GET /kb/stale-cards`（A3 已交付数据面）+ 菜单扫描 diff 定期输出漂移日报。触发条件：KB 卡量过 50 张或出现第一次"漂移没及时发现导致回放失败"的真实事故后再建定时器；当下手动 `curl /kb/stale-cards` 即可，不值得为它建 cron 基础设施。

## B2 KB 业务分层标签（biz_tags）→ 伪需求（过早）

- **批判**：消费方是"按业务域聚合的覆盖报表"——而 coverage API 今天刚上线，**消费者数量为零**。386 个功能节点、29 张卡的规模下，没有真实读者提出过"按业务域看覆盖"。这是"为报表建标签、为标签建报表"的自循环，典型的过早优化。
- **成本再评估**：卡片加字段是 additive 的、随时可补——**推迟的代价≈0**，现在做的收益≈0。推迟没有损失，就是不该现在做的最强信号。
- **触发条件**：coverage 端点出现真实消费方（前端报表页 / 伙伴端拉取），且对方明确要业务维度视图。

## B3 执行结果关联缺陷单 → 伪需求（当前形态）；重新表述为「失败上报伙伴工单」

- **批判**：本仓执行失败的闭环**已经存在**：batch item errorMessage + 站内信 + form-structure-heal 自愈 + rerun-replay 失败步重跑。关键检验问题：「上周失败的批量 item，今天还有人在看吗？」——没有。失败是当场消费的（操作员当场看、当场重试），不存在跨天跟踪的失败长尾。伙伴需要缺陷单，因为它向测试团队**交付执行结果**；本仓交付物是**录制的轨迹资产**（推送伙伴平台），失败不是交付物。
- **自建缺陷域模型**（表+API+状态机）在本仓没有归属：没有缺陷详情页、没有处理流程、没有统计消费。
- **种子（观察名单）**：若未来伙伴端主动要求"失败自动进我们工单系统"，正确形态是**推送适配器**（调对方 API，一个薄模块），依然不需要本仓自建缺陷模型。触发条件：伙伴端书面提出该诉求。

## B4 晋升工作台（staging → Web 审核 UI）→ 伪需求（痛点错位）

- **批判**：诚实修正——staging 现有 **46 条积压**（4 天），积压是真的。但积压的瓶颈是**没有人去审**（审查是低频高判断动作：每条都要人判断知识真伪），不是 CLI 不方便。Web 工作台解决"审的时候点鼠标代替敲命令"，不解决"没人审"——做了 UI 积压照旧。
- 另一层：审核是高判断密度操作（要对照卡片上下文、湿测证据），天然适合 CLI + 编辑器（看 JSON、grep 轨迹、改字段），Web 表单反而降低效率。且 /api/docs 是唯一前端契约，为内部工具建前端页面违背产品面定位。
- **低成本替代**（若要做，做这个）：给 `promote.py` 加 `--list` 人类友好分组输出（现在 proposal 已有分组，只差可读性），覆盖 90% 的"不知道现在有什么可晋升"问题。触发条件：staging 日均新增 20+ 条且出现多会话并发晋升冲突时，再议工作台。

## 总判定与建议

| 项 | 判定 | 重新表述（观察名单） | 触发条件 |
|---|---|---|---|
| B1 定时触发录制批量 | **伪**（形态错配） | KB/菜单漂移定时巡检 | 卡量 50+ 或首次漂移事故 |
| B2 业务分层标签 | **伪**（过早，零消费者） | — | coverage 出现真实消费方且要业务维度 |
| B3 缺陷单关联 | **伪**（失败无长尾） | 失败上报伙伴工单（薄适配器） | 伙伴端书面提出 |
| B4 晋升工作台 | **伪**（痛点=没人审） | promote.py `--list` 可读输出 | 日均 20+ 条且并发冲突 |

- **调研的价值重申**：对照的意义不是照搬能力清单，而是逼出「我们到底缺什么」——答案是 A 级三项（溯源/覆盖/变更反查），已全部落地并有真实消费场景；B 级经此审查确认全部缓行，C 级维持不对标。伙伴体系六节点闭环对其成立，是因为它是执行平台；我们是录制工具+KB，**不欠那些能力**。
- 若用户仍希望推进某项：B1 的巡检种子和 B4 的 `--list` 是两个半天级小活，可作为"低成本满足好奇心"的选择；B2/B3 建议明确搁置。
