# 伙伴技术交流会消化调研——「全景AI」测试智能化体系 vs JS-gen 现状（2026-09-05）

> 调研方式：8 张交流会截图视觉转写（底稿 `tmp/research/partner-exchange-notes.md`，不入库；低清晰度处已标注【低置信】）→ 两路只读子智能体对照盘点（KB 体系线 / 执行调度线，file:line 级证据）→ 主线程汇总分级。

> 一个基本判断先行：对方定位是「测试智能化平台」（需求→用例→执行→覆盖全链），我们定位是「浏览器自动化录制/回放 + 信贷 KB」。**不整体对标，只取能让本仓 KB 从"文件卡片"升级为"带溯源与覆盖度量的资产"、并补齐执行外围闭环的部分。**

## 3. 化为己用：分级建议

### A 级——立即可吸收（低成本高价值，与现有架构强契合，纯外围不动引擎）

**A1. 知识溯源 ID 化**（吸收图 4「溯源」精髓）
- 现状：`data/kb/flows/*.json` 的 `source` 是自由文本（"K1 2026-08-31 + 交易 203-206 + 轨迹 260813…"），人可读机器不可查；MySQL 轨迹库与 KB 文件库是孤岛。
- 做法：卡片 schema 增**可选**字段 `source_refs: { trajectoryIds: [], txNos: [], dates: [] }`；写一次性迁移脚本解析现有 25 卡 source 文本回填；`store.py`/`recall.py` 零改动（可选字段向后兼容）。此后"这条知识来自哪次录制"可程序化反查，也是 A2/A3 的数据基础。
- 锚点：`scripts/kb/store.py:12-17`、`data/kb/flows/*.json`。工作量：半天内。

**A2. 覆盖分析最小闭环**（吸收图 1「覆盖分析」）
- 现状：functionId 绑定与功能树骨架全在，只缺读侧度量。
- 做法：新增只读 service + route——按系统/模块/功能节点统计绑定轨迹数、最近执行时间、批量执行成功率；输出「未覆盖功能清单」（树上有节点、零绑定轨迹）。纯查询，零引擎改动。
- 锚点：`hierarchy-tree-query.js`（昨日拆分正好腾出了树查询模块）、`batch-recording-dao.js`、`trajectory-meta-service.js:167-234`。工作量：1-2 天。

**A3. 变更→影响反查**（吸收图 1「变更分析→知识资产」回流的最小版）
- 现状：`system_menu_change_log` 只写不读——菜单改名/迁移/删除后没人知道伤了哪些流程卡和轨迹。
- 做法：新增只读影响分析 API——输入 changeLogId（或系统节点+时间窗），输出受影响流程卡（按 `menu_path` 前缀匹配）+ 受影响绑定轨迹清单；扫描报告里给出提示。与 A1 联动后可精确到 source_refs 轨迹。
- 锚点：`menu-change-log-dao.js`（补一个查询方法）、`data/kb/flows` 的 menu_path。工作量：1 天。

> A1+A2+A3 合起来 = 伙伴「溯源↔召回↔传导」三角中我们缺的两条边（召回那条边已有），且全部是外围读侧，与正在开发的引擎/KB 热区几乎不相交。

### B 级——中期立项（需小型基础设施或外部决策）

**B1. 批量任务定时触发**（图 7 三模触发）：控制面已有 setInterval 泵与启动恢复（`trajectory-batch-service.js:450-473,535-607`），补一张 `batch_schedule` 表 + 每分钟检查的轻量调度器（不引 cron 库，自清理 interval 模式仓里有三处先例），即可支持"每日回归巡检"场景。事件触发（外部钩子建任务）待有真实事件源再做。
**B2. KB 业务分层标签**（图 5 的裁剪版）：**不建议照搬 L0-L5 六级**——我们的单元是"流程卡"（约等价 L4/L5），全层级属过度建模。建议只加 `biz_tags: { domain, category, stage }` 三字段（L0-L2 级），让"授信域/用信类/贷后阶段"可聚合统计，配合 A2 覆盖报表按业务维度出数。业务与系统建模分离的思想吸收，粒度裁剪。
**B3. 缺陷单关联**（图 7）：我们生态没有内部缺陷平台，需用户决策对接目标（公司工单系统 API / 导出报告替代）。最小等价物：失败 item 聚合成"问题工单"实体（表+API+闭环状态），先内部闭环再谈外接。
**B4. 构建治理流程化**（图 3）：promote.py 的 CLI 人审升级为 `/api/docs` 内的晋升工作台（列表/对比/一键晋升），把"审核与治理"从个人 CLI 变产品面。依赖前端排期。

### C 级——明确不对标（写明理由防止后续误跟）

- **语义/向量召回**：25 卡规模下 hash+keywords 湿测全命中；卡量上百且出现误召回痼疾时再评估，且须先解决 LLM 网关稳定性（记忆：网关间歇失联史）。
- **知识地图 UI**：本仓产品面是 API（`/api/docs` 唯一契约），知识地图退化为 A2 覆盖报表 JSON 即可，不做重 UI。
- **智能问答/模型咨询交互层**（图 2 三层交互）：与录制回放主业无关，不建。

## 4. 与当前工作线的关系

- 引擎/KB 线正开发中（KB 卡扩充、引擎自主闭环冲刺）。A1/A2/A3 均为外围读侧与 schema 可选字段，热区不相交，可并行立项；B1 动 `trajectory-batch-service.js`（批量线文件）须与批量任务使用方协调窗口。
- 建议落地顺序：**A1（半天，数据基础）→ A3（1 天）→ A2（1-2 天，含报表 API）**，B 级按季度规划。
- 本报告不改任何代码；若用户认可 A 级，按新协议（开工声明→实施→收工回报）另行立项。
