# Agent 交付评审规范（reviewer 方法论）

> 给谁用：Lead（派工与仲裁）、reviewer（出结论）、各实施线（自查交付质量）。  
> 关联：各 plan 的 Reviewer Checklist；KB 线 G1/G2/G3 门禁实操见 [`reports/2026-09-09-kb-recall-eval-g1-g2.md`](../reports/2026-09-09-kb-recall-eval-g1-g2.md)。  
> 日期：2026-09-09（首版，源自 KB 召回评测常态化线的实审复盘）

## 1. 角色与边界

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 实施方 | 实现、自证、落证据、按协议声明与提交 | 不自我验收、不改判据、不代写 reviewer 结论 |
| reviewer | 读 diff、独立复现、反作弊、出三态结论 | **不替实施方改代码**（除非 Lead 明确要求）；**不代提交** |
| Lead | 裁决歧义、批准阈值/冻结变更、派工 | 不跳过门禁直接放行 |

**为什么 reviewer 不能顺手修**：一旦同一个人既实现又验收，"审"就退化为"自证"，门禁失去意义。reviewer 的产出是**判断**，不是补丁。

## 2. 证据分级（自述永远排最后）

| 等级 | 形态 | KB 线实例 |
|---|---|---|
| 最弱 | 实施方自述 | 「语义不变」「6/6 MATCH」「与本线零依赖」 |
| 弱 | 实施方贴的命令输出 | 他们的 `T1-struct.txt` |
| 中 | reviewer 复跑他们的命令 | 跑 `characterize-flow-card-recall` → 17 passed |
| 强 | reviewer **自写**的探针 | 130 条 `matchFlowForAtom` vs `rankFlowCards(k=1)` 逐字段比对 → 0 差异 |
| 最强 | reviewer 看到**反例** | 实施方报「7 红」，实跑是「5 红」 |

推论：
- 读 pin/file 只能证明「有人写了断言」，**不能证明断言为真** → 关键不变量要自己重算。
- 「文件集不相交」**不能用区间 diff 判**（`a~1..b` 会混入他线提交）→ 必须**逐笔 `git show --stat`**。
- 「全绿」不是结论：门禁 FAILED 时先判**是否与被审线耦合**，再决定算谁的账。

## 3. 标准流程（六步）

1. **读 diff 不读自述**：逐笔看 `git show`，重点看 pin 是否被削弱（恒真化/删除/跳过）、有无越界文件。
2. **复跑声明命令**：DoD 矩阵 + 既有基线套件，记录真实 exit code。
3. **独立探针**：对每个关键不变量写自己的最小复现，不采信对方输出。
4. **反作弊清单**：逐条对照（见 §8），任一命中即 FAIL。
5. **门禁自证**：对该红会红的路径，**自己动手制造失败**，确认它真的红。
6. **判定**：`PASS` / `FAIL`（附复现命令）/ `DONE_WITH_CONCERNS`（写明未闭环风险）。

## 4. 抽检类门禁（G1 型：标注/数据是否独立）

目标：判断「这份真值/标注是独立产出的，还是反推实现得到的」。四道设计缺一不可：

1. **先给输入，后给真值**。选样脚本输出里**扣掉 gold 字段**——同屏并排会让人附和而非判断。
2. **只看语料，不跑被审件**。用最笨的办法（词表 dump + 纯字符串 grep）自判；跑匹配器等于让被审对象替你思考。
3. **剔除无效样本并披露**。若抽中自己此前标注的条目，**单独剔除计数**（自己复核自己 = 没检）。
4. **抽最易注水处**。multi-gold、边界样本、最容易"怎么说都对"的条目优先抽；按层配额抽样，避免全落简单层。

判据沿用 plan 原文（例：分歧 >10% 回炉），**reviewer 不临场改标准**。

## 5. 阈值/门禁类审查（G2 型）

审之前先问：**这个指标的方差从哪来？**

- 有随机性（抽样/温度/并发）→ 余量必须覆盖噪声，否则天天假红；
- **确定性**（冻结数据 + 冻结语料 + 确定性算法）→ **无运行间方差**，余量只服务于「有意变更」，此时的余量上限就是可接受的头部空间，不算"太松"。

与松紧无关、但最容易翻车的三件事，必须查：

| 检查 | 为什么 | KB 线实例 |
|---|---|---|
| **比较符方向** | 写反不会报错，只会永远绿 | 读 `compareWithBaseline`：`ok = current >= baseline − margin` ✓ |
| **双向验收** | 只测"通过"没意义，要证明"该红会红" | 对自身基线 exit 0；对更严基线 exit 1 且六项全 FAIL ✓ |
| **预算类断言是否真强制** | 延迟/成本常被写成只打印不判定 | `warmP95>50 / coldP95>200` 真参与 pass 计算 ✓ |

## 6. 结论纪律

- **三态**：`PASS` / `FAIL`（附复现命令）/ `DONE_WITH_CONCERNS`（功能达成但有未闭环风险，必须写明）。
- **区分「回归」与「口径」**：数字变差时先跑上一轮基线证明算法未动，再归因到数据/口径；**若旧基线也掉了，直接 FAIL，不替对方找解释**。
- 实例：v1 Acc@1 0.650 vs hold-out 0.90 —— 先跑 hold-out 得 6/6 MATCH，才背书「分层量化存量缺口，非回归」。
- **数字带区间**：给出 Wilson 95% CI（n=100 的 0.650 → [0.553, 0.736]），避免被读成精确值。
- **未验证就写「未验证」**：环境不可达时（如 DB 断连）不拿对方 pin 当结果。

## 7. 更正与撤回机制

- **「可疑」与「定罪」分开**：证据不足时宁可从严标注（`必改`），但必须写明是**哪条命令、什么现象**，便于日后证伪。
- **复现环境本身是变量**：`EPERM`/`spawnSync`/`WinError 5` 等系统级错误，先怀疑自己的沙箱/权限，再怀疑实现。
- **能证伪就立刻撤回**：环境条件一变，第一时间复跑；撤回要写进结论文件（谁撤回、依据、结论变化），**并明确告知对方"无需改动"**——因为假阳的成本是别人的时间。
- KB 线实例：`execSync('git rev-parse')` 曾被判「必改·阻断 T4」，沙箱放开后复跑 exit=0 → 撤回为「环境假阳，可选加固」。

## 8. 常见假阳 / 假阴清单

| 类型 | 表现 | 对策 |
|---|---|---|
| 假阳·环境 | 沙箱禁 spawn/piped stdio、临时目录不可写 | 换执行环境复跑后再定性 |
| 假阳·数据 | DB 数据型断言（截图 id、给定 traj） | 判「数据依赖红」，不记在被审线 |
| 假阳·偶发 | 门禁内红、单跑绿 | 单跑复现 + 标注 flaky |
| 假阴·断言削弱 | pin 被改成恒真/删除/跳过 | diff 里逐条看 `-` 行 |
| 假阴·比较符 | 门禁恒绿 | 读比较函数 + 自造失败 |
| 假阴·抽样偏差 | 只抽头部/简单样本 | 分层配额 + 抽易注水处 |
| 假阴·口径漂移 | 指标定义悄悄变（如多 gold 分摊 vs 二值） | 要求把口径写进 JSDoc/文档 |

## 9. 记录与落盘

每个 gate 出一份结论文件（`docs/superpowers/reports/<date>-<line>-<gate>.md`），必含：

1. 被审 commit 区间与逐笔范围核对；
2. reviewer 实测 vs 实施方声明的逐项对账表；
3. 反作弊清单结论；
4. 未验证/环境受限项（如实写）；
5. 三态结论 + 放行条件 + 遗留移交。

结论文件与代码分开提交；**不代提交实施方的代码**。

## 10. 复用清单（派工时抄进 plan）

- [ ] 明确 gate 及放行条件（如 G1 抽检 → G2 阈值 → G3 终局）
- [ ] 明确「reviewer 不代提交、不替实现改代码」
- [ ] 明确阈值/冻结类变更的批准人与记录位置
