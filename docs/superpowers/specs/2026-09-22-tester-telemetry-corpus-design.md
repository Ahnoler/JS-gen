# 测试人员操作语料采集与知识化设计

| 项 | 内容 |
|---|---|
| 文档状态 | 设计待评审 |
| 版本 | v1.0 |
| 日期 | 2026-09-22 |
| 影响面 | 新增采集插件（独立交付物）+ 本系统服务端新增语料层与处理流水线；不改动现有录制/回放链路的既有行为 |
| 代码基线 | `eab6c041`（文中 `file:line` 以该提交为基准，代码前进后按符号名检索） |

**摘要**：本设计定义如何把测试人员在被测系统上的真实操作过程，采集为一类新的知识供给源，用于提高 UI 录制的准确性与效率。交付物包含两部分——一个独立的浏览器采集插件，以及本系统侧新增的语料存储、归集、审核与晋升链路。设计不引入新的轨迹生成方式，采集产物不以"交易"为单位，而是以"证据片段"为单位，最终用于补全流程卡字段、产出定位先验与路径先验。

---

## 1. 概述

### 1.1 背景

本系统的流程卡（`data/kb/flows/*.json`，共 84 张）现有三个供给源：需求文档、湿测、录制回流（`data/kb/staging/staged_flows.jsonl`）。三个源存在共同的局限——**只产"正确路径"**：需求文档描述的是应然流程，湿测受协议限制（禁写操作），录制回流来自执行机自身跑通的轨迹。

实测 84 张流程卡的字段填充度（2026-09-22）呈现出清晰的分界：

| 字段 | 非空 | 稀疏率 | 性质 |
|---|---|---|---|
| `biz_key_prefix` | 14/84 | 0.83 | 业务单号前缀 |
| `field_deps` | 15/84 | 0.82 | 字段联动关系 |
| `state_actions` | 20/84 | 0.76 | 状态×动作矩阵 |
| `exceptions` | 31/84 | 0.63 | 异常分支 |
| `rules` | 49/84 | 0.42 | 隐藏业务规则 |
| `aliases` | 84/84 | 0.00 | 别名 |
| `menu_path` | 84/84 | 0.00 | 菜单路径 |
| `nodes` | 84/84 | 0.00 | 节点图 |
| `preconditions` | 83/84 | 0.01 | 前置条件 |

**结论：文档能提供的字段已接近饱和；稀疏的字段全部属于"操作性知识"**——单号前缀要在真实生成单号时才可见，字段联动要在触发时才发现，状态动作矩阵要求操作者真的处于该状态。这类知识的最优供给源是测试人员的真实操作过程。

同时，测试人员在日常测试中存在大量重复操作（对同一功能反复测试）与探索性操作，其中携带了现有数据完全没有的三类信息：**使用频次、常见弯路、系统拒绝行为**。

### 1.2 目标

| 维度 | 定义 | 所需输入 |
|---|---|---|
| 录制准确性 | 录制产物回放能跑通 | 定位稳定、步骤正确、成功可判定 |
| 录制效率 | 单笔录制的耗时与返工次数 | 知道正确路径、无需人工补断点与确认 |

### 1.3 范围

**包含**：

- 采集插件（独立交付物，浏览器扩展形态）的需求与架构设计
- 插件与本系统之间的接口契约
- 本系统侧的语料存储、处理流水线、审核机制与消费路径设计
- 为支撑上述内容所需的系统侧改造清单

**不包含（非目标）**：

1. **不以语料自动生成轨迹。** 轨迹是可编辑的产品资产（带断言、可回放），语料是统计证据（含噪、含误操作、会过期）。若由语料自动产出轨迹，将生成大量表面完整、实则混入试错步骤的资产，污染轨迹列表。两者的连接方式仅为单向：`语料 → 证据 → 人审 → 卡字段` 与 `语料 → 统计 → 先验 → 录放决策输入`。
2. **不要求测试人员理解本系统的数据要求与交易分类体系。** 采集插件不得要求用户提供任何需要"熟悉本系统分类"才能填写的字段。
3. **不在采集插件内承载业务判断。** 插件的采集范围限定为客观观测。
4. **本次不实现采集插件**（由独立项目交付），本设计只定义其需求、契约与约束。
5. **不改变现有录制与回放链路的既有行为**，除第 9 节列出的改造项之外。

### 1.4 术语

| 术语 | 定义 |
|---|---|
| **会话（session）** | 测试人员通过插件界定的一段有目的的操作区间，由「开始」与「结束」划定 |
| **片段（segment）** | 会话内的一个证据单元；本文中以原始事件为主 |
| **语料层** | 存储原始采集数据的只读层，可过期、可清理 |
| **知识层** | 流程卡及其字段，可编辑、带出处锚点 |
| **评测集** | 冻结的召回质量标注集（`kb-recall-eval.v*.json`） |
| **证据** | 从片段中归集出的、指向某个卡字段的观察记录 |
| **SUT** | 被测系统（本文场景下为信贷系统） |

## 2. 设计原则

### P1 · 采集契约要薄，服务端要厚

采集插件安装在测试人员的本地浏览器上，**升级成本高、覆盖周期长**；本系统则在持续迭代。因此推给插件侧的每一份智能，都等于一份"冻结的智能"。

**设计约束**：插件侧只产出客观观测（DOM 事件、元素快照、页面标识、网络元数据、时间戳）；所有结构归纳、业务分类与语义推断均在服务端完成。由此，无论服务端如何演进，已采集的语料均无需重采，测试人员也无需配合第二次。

### P2 · 语料 / 知识 / 评测集三层物理隔离

| 层 | 位置 | 生命周期 | 性质 |
|---|---|---|---|
| 语料层 | 新增（见 6.1） | 只读、可过期、可清理 | 量大、含噪、含误操作 |
| 知识层 | `data/kb/flows/*.json` | 可编辑、有出处锚点 | 晋升产物 |
| 评测集 | `scripts/characterization/fixtures/kb-recall-eval.v*.json` | 冻结 | 变更须经审批 |

**语料不得进入评测集。** 语料在形式上接近 ground truth，但包含误操作，一旦作为评测标注将导致召回评测失真且难以察觉。语料只能作为审核环节的第三方参考证据。此约束为既有纪律（"扩充/修订评测集时禁止先跑匹配器反推 gold"）的延伸。

### P3 · 客观观测在采集侧，业务判断在服务端

判别标准：**凡需要"知道这是什么业务"才能产出的字段，不得出现在采集契约中。**

### P4 · 采集侧丢弃不可逆，服务端忽略可逆

采集侧一旦不投递，信息永久丢失；服务端收到后不使用，数据仍在，未来可按新口径重新消费。因此除第 4.6 节明确规定的「作废」场景外，采集侧一律投递，由服务端做分流。

## 4. 采集端设计（浏览器插件）

### 4.1 组件架构

采用 **Manifest V3** 扩展（Chrome / Edge 现行标准；规避 MV2 淘汰风险与 service worker 生命周期不确定性）。

| 组件 | 职责 | 关键约束 |
|---|---|---|
| **content script** | 事件捕获、元素定位快照生成、页面反馈观察 | 运行于被测页面上下文，须与 SUT 前端隔离，避免全局污染 |
| **service worker** | 会话状态机持有、本地缓冲落盘、投递控制面、状态广播 | **会话状态必须由 service worker 持有**——页面重载或标签切换不应丢失会话 |
| **popup / side panel** | 测试人员交互面（开始 / 结束 + 状态展示） | 不使用 modal，不打断页面操作 |
| **options page** | 控制面地址、SUT 域名白名单、操作员标识绑定 | 由实施方配置，测试人员不修改 |
| **action badge** | 采集状态指示（红点/灰点） | 一级重要性，见 4.7 |

> **设计说明**：会话状态不放 content script，是因为被测系统是 SPA，页面重载、路由跳转、标签切换都会重建 content script 上下文，放在页面侧会导致会话状态丢失。

### 4.2 权限与激活范围

遵循最小权限原则：

| 权限 | 用途 | 说明 |
|---|---|---|
| `host_permissions` | 仅申请 **SUT 域名 + 控制面域名** | 不使用 `<all_urls>` |
| `scripting` | 注入 content script | |
| `storage` | 配置与轻量状态 | 大缓冲使用 IndexedDB |
| `activeTab` | 读取当前标签页状态 | |

**不申请的权限及原因**：

- `webRequest`：网络元数据通过页面侧的 `XMLHttpRequest` / `fetch` hook 获取。相比 `webRequest`，此方式权限更轻，且能直接关联到发起请求的页面动作与元素上下文。
- `tabs`（全量）：页面标识从 content script 内读取 `location` 即可获得，无需标签页枚举权限。
- `cookies` / `history` / `downloads`：无需求。

**激活范围限定**：插件仅在配置的 SUT 域名白名单上激活；在白名单外的页面不注入、不采集。

### 4.3 注入与事件捕获

**注入时机**：`run_at: document_start`，早于被测页面脚本，避免监听被页面代码覆盖或在初始化阶段丢失早期事件。

**事件捕获策略**：

| 策略 | 原因 |
|---|---|
| 使用**捕获阶段**监听（`capture: true`） | 避免被测系统的 `stopPropagation` 吞掉事件 |
| **以 `mousedown` 为定位主源**，`click` 为辅 | `click` 事件到达时页面可能已跳转，事后取元素会取到新页面的元素。既有手工录制器已记录此问题（`scripts/manual_recorder/recorder.py` 的文件头 TODO 明确说明该缺陷，并把"改用 mousedown 上报"列为可行方案） |
| 监听 SPA 路由变化（`hashchange` / `popstate`） | 被测系统为 hash 路由 SPA，`pageLevelKey` 需随路由重算 |
| `all_frames: true` 注入 iframe | 快照中记录 frame 路径，回放时按 frame 定位 |

**捕获的 DOM 事件类型**：

| 事件 | 用途 |
|---|---|
| `mousedown` | 点击类动作的定位主源 |
| `click` | 动作确认与结果关联 |
| `input` / `change` | 值变更（**不记录值原文**，见 4.8） |
| `blur` / `focus` | 字段进出、blur 是否触发提交 |
| `keydown`（仅退格/删除键） | 纠错信号：退格计数、清空重填判定 |
| `scroll` | 仅记位置变化（用于判断页面是否发生自动滚动），不进入事件流主体 |

**网络观察**：hook `XMLHttpRequest` 与 `fetch`，记录 `{method, urlPath, status, durationMs}`。**仅记录 path 模板与状态码，不记录 query、请求体与响应体**。

**页面反馈观察**：`MutationObserver` 监听承载反馈的节点出现，用于采集系统级反馈（这是第 6.3 节判别器的输入）：

- `el-message` / `el-message-box` 系列（成功 / 警告 / 错误通知）
- `.el-form-item__error`（表单校验红字）
- 对话窗与抽屉的开合

`MutationObserver` 须限定观察子树与属性范围（见 4.8 性能约束）。

### 4.4 元素定位快照生成

定位快照是插件侧唯一需要在页面上下文内计算的内容。

**处理流程**：

1. 从事件 `target` 向上寻找"可交互语义元素"（跳过纯布局包装节点）
2. 生成 `xpath`（语义锚定，优先级见 5.3）与 `xpath_full`（绝对路径兜底）

**执行时机**：必须在事件回调的同步阶段或紧随其后的微任务中抓取——被测系统是 Vue 应用，DOM 节点会被重建，延后取值会取到失效或不同的节点。

> 定位质量直接决定回放命中率，因此 `xpath` 的生成必须遵循 5.3 的语义锚定优先级。定位质量本身**不在采集端自评**，由服务端依据实际回放结果统计（见 7.1）。

### 4.5 会话模型与状态机

会话由「开始」发起，由「结束」收尾；「结束」要求给出三种结果之一：

```
     idle ──开始──▶ recording ──结束(通过) ───▶ ended ──投递──▶ idle
                        │      ──结束(不通过) ─▶ ended ──投递──▶ idle
                        │      ──结束(作废) ───▶ idle（本地缓冲清空，内容不投递）
                        │
                        └──空闲超时──▶ ended（置 autoClosed，置信度降权）
```

| 状态迁移 | 行为 |
|---|---|
| idle → recording | 分配 `externalSessionId`，开启缓冲写入 |
| recording → ended（通过 / 不通过） | 写入 `verdict`，封存缓冲，触发投递 |
| recording → idle（作废） | **清空本地缓冲，不投递内容**；仅上报计数（见下） |
| 空闲超时 | 自动转入 ended，`autoClosed: true`，无 `verdict` |

**三种结束结果的语义**

| 结果 | 用户语义 | 系统去向 |
|---|---|---|
| **通过** | 这段操作正常完成 | 投递；作为路径正样本 |
| **不通过** | 结果不符预期，或发现了系统问题 | 投递；作为异常/规则证据（见 6.5） |
| **作废** | 这段操作无效（误操作、探索、中途放弃） | **本地丢弃，等价于未开始** |

**「作废」的处置**：该动作即结束该段并丢弃，不投递内容。作废后须清空本地缓冲，否则误操作后残留数据仍可能被后续逻辑带出。由于「作废」本身已表达"丢弃"意图，无需用户再单独执行其他动作。

**作废的计数上报（轻量观测，可选实现）**：作废时仅上报两个数字——累计作废会话数与该段大致时长，不含任何内容。用于观测采集覆盖率：若作废比例过高，说明交互设计存在问题。此项为可选项，不实现不影响主体功能。

**超时兜底**：不做弹窗提醒（会打断操作流）。空闲超时自动收尾并标记 `autoClosed`，该段置信度自动降权。

### 4.6 本地缓冲与投递

| 项 | 设计 |
|---|---|
| 缓冲介质 | IndexedDB，按 `(externalSessionId, segmentIndex)` 建索引 |
| 写入时机 | 事件产生即写入，避免会话中断导致数据丢失 |
| 投递时机 | 会话 ended 后触发；支持分批 |
| 断网 / 控制面不可达 | 指数退避重试；缓冲保留至成功或过期（建议 7 天） |
| 幂等 | 投递携带 `(externalSessionId, segmentIndex)`，服务端据此去重（见 5.6） |
| 作废 | 清空该会话的缓冲记录，内容不投递 |

### 4.7 测试人员交互面

**采集状态指示（一级重要性）**

静默采集最大的风险不是"未采到数据"，而是**"用户以为在采集，实际未在采集"**——用户整段测试后系统零数据，双方都不知情。因此需要一个持续可见的状态指示：

- `chrome.action.setBadgeText` + 背景色：**红点 = 采集中，灰点 = 未采集**
- 零交互成本，但避免整段数据浪费

**两个动作**

| 动作 | 必需性 | 交互成本 | 产出 |
|---|---|---|---|
| 开始 | 必需 | 1 次点击 | 会话起点 |
| 结束 | 必需 | 1 次点击（三选一） | 会话终点 + 结果判定 |

**「结束」的三种结果**

| 结果 | 用户语义 | 系统处置 |
|---|---|---|
| **通过** | 这段操作正常完成 | 投递；进入路径正样本 |
| **不通过** | 结果不符预期，或发现了系统问题 | 投递；进入异常/规则证据（见 6.5） |
| **作废** | 这段无效，不必记录 | 本地丢弃，等价于未开始 |

**「开始 / 结束」为什么必需**：测试人员在被测系统上会进行大量操作，并对同一功能反复测试。若采用连续采集，将产生大量无意义的观测数据。开始/结束提供**意图边界**——按下开始时表示"接下来这段是有目的的操作"，按下结束时表示"这段的结论成立"。三种结束结果同时承担了**结果判定**与**噪声剔除**两项职责，因此不需要额外的动作（如单独的"作废"或"结果选择"）。该语义是第 6.5 节重复归并规则的必需输入。

**「不通过」自动附带现场快照**（用户零额外成本）：当前截图、当前页面上的业务单号、当前 `pageLevelKey`、最近 30 秒的网络请求元数据、当前可见的错误提示。该快照用于两处——服务端的异常证据归集，以及插件自身为测试人员生成缺陷复现材料。

**「会话名称」（可选）**

该字段可选填、可跳过，有两个用途：

1. **作为召回查询的一部分**。会话名称是用户对这段操作的语义概括，可作为查询输入送入现有的 `flow-card-recall` 召回器，与 `data/kb/staging/recall-events.jsonl` 中已记录的 query 同源。**不得将名称直接作为交易分类结果**——用户的命名习惯与流程卡命名体系不一致，直接匹配会产生错误。
2. **作为口语语料**。该字段是真实口语表述的零成本来源，且带页面上下文与业务单号锚定，可作为口语桥接方向（见附录 B）的语料输入。

**交互约束**

- 一级按钮不超过 2 个（开始、结束），其余收纳进二级界面
- 不使用 modal，不打断操作流
- 所有可选字段默认可跳过，不设"必须填写才能继续"

### 4.8 隐私、安全与性能约束

**隐私与安全**

| 约束 | 设计 |
|---|---|
| 输入值原文 | **不得离开浏览器**。脱敏在插件侧完成，仅传输长度、类型或枚举判定结果 |
| 业务敏感数据 | 客户姓名、证件号、金额明细等不上传 |
| 网络数据 | 仅 path 模板 + 状态码，**不传 query、请求体、响应体** |
| 凭据 | 不采集 cookie / token / session id |
| 操作员身份 | 以脱敏引用（哈希/工号）形式传输，不传姓名 |
| 传输 | HTTPS，携带鉴权令牌 |
| 截图 | 默认不上传；如后续需要，须单独开关与独立存储策略 |
| 激活范围 | 仅 SUT 域名白名单 |

**性能约束**

被测系统是重表单应用，任何可感知的卡顿都会导致插件被卸载。硬性约束：

| 项 | 约束 |
|---|---|
| 事件回调 | 只做 O(1) 记录（元素引用 + 类型 + 时间戳），不做任何遍历 |
| 快照计算 | 定位字段在微任务中同步抓取；昂贵计算放 `requestIdleCallback` |
| `input` 事件 | 300ms 去抖，避免逐字符触发 |
| `MutationObserver` | 限定观察子树与 `attributeFilter`，不观察 `subtree: true` 全量 |
| 内存 | 缓冲定期落盘并释放；单会话内存设上限 |
| 目标 | 对被测页面帧率的影响不超过 1 帧 |

**与 SUT 前端的隔离**：content script 不得污染页面全局命名空间，不得修改被测页面的 DOM 结构或样式（除插件自身的状态浮层，且须使用独立命名前缀与最高 z-index 隔离）。

### 4.9 分发、升级与版本兼容

| 项 | 设计 |
|---|---|
| 分发方式 | 企业内分发（Chrome 企业策略 / 自建 CRX / 开发者模式加载），视 IT 策略选择 |
| 版本上报 | 会话头携带 `client`（插件名 + 版本），服务端按版本归因 |
| **向后兼容** | **服务端必须容忍旧版插件缺失字段**。这是 P1 原则的现实理由：插件升级周期以周计，服务端迭代以天计 |
| 灰度 | 先小范围测试人员试用，验证采集覆盖率与性能影响后再扩大 |
| 契约演进 | 新增字段为可选；删除或改变语义的字段须服务端先兼容一个版本周期以上 |

### 5.1 会话头

| 字段 | 必填 | 类型 | 说明 |

| `externalSessionId` | ✓ | string | 幂等键，长度 ≤128 |
| `operatorRef` | ✓ | string | 脱敏后的操作员引用（哈希/工号），非姓名，≤64 |

| `sutHost` | ✓ | string | 被测系统 host |
| `sutVersion` | ✓ | string | **被测系统版本**。SUT 升级是定位失效的首要原因，缺少该维度将无法区分"录制缺陷"与"系统变更" |
| `client` | ✓ | string | 插件名 + 版本，如 `credit-tracer/1.0.0` |
| `segments` | ✓ | array | 长度 1..2000，超限分片投递 |
| `operatorRole` | ○ | string | 岗位（客户经理 / 审批人 / 贷后），不同角色的语义不同 |
| `autoClosed` | ○ | bool | 是否因空闲超时自动收尾 |
| `verdict` | ○ | enum | `pass` / `fail`（结束时的结果选择）。缺省表示空闲超时自动收尾、用户未作选择；「作废」的会话不投递，故不携带该字段 |

| `discardedSessions` | ○ | int | 客户端累计已作废并丢弃的会话数（仅计数，见 4.6） |

### 5.2 事件流

会话内每个片段的基本形态：

```json
{
  "segmentType": "raw",
  "segmentIndex": 42,
  "ts": 1758335412300,
  "pageLevelKey": "page:https://credit-test.example.com/#/product/coreMap",
  "domEvent": "mousedown",
  "element": { "...见 5.3..." },
  "timing": { "sincePrevMs": 3200, "dwellMs": 850, "inputDurationMs": 0, "backspaceCount": 0, "clearedBeforeTyping": false },
  "net": [
    { "method": "POST", "urlPath": "/api/v2/coreProduct/query", "status": 200, "durationMs": 412 }
  ],
  "feedback": [
    { "level": "error", "text": "利率不能为空", "selector": ".el-form-item__error" }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `segmentType` | ✓ | 恒为 `raw`（原始事件）。无法归类时用 `unknown`，**不得猜测** |
| `segmentIndex` | ✓ | 会话内序号，从 0 连续递增 |
| `ts` | ✓ | 动作发生时刻（epoch ms），**非落库时间** |
| `pageLevelKey` | ✓ | 页面标识，格式见 5.4 |
| `domEvent` | ✓ | 触发事件类型：`mousedown` / `click` / `input` / `change` / `blur` / `focus` / `keydown` / `nav` |
| `element` | ✓ | 元素定位快照，见 5.3 |
| `timing` | ○ | 操作内行为与间隔，见下表 |
| `net` | ○ | 该动作触发的网络请求元数据 |
| `feedback` | ○ | 该动作触发的系统反馈 |

> `marker` 字段为后续版本预留（人工标记能力），当前版本不使用（见附录 C 待评审决策点）。

**`timing` 字段说明**

| 字段 | 用途 | 是否必填 |
|---|---|---|
| `sincePrevMs` | 与上一动作的间隔 | ○（可由 `ts` 推导，仅为便利） |
| `dwellMs` | 在目标元素上的停留时长 | ○ |
| `inputDurationMs` | 输入耗时 | ○ |
| `backspaceCount` | 退格次数 | ○（纠错信号） |
| `clearedBeforeTyping` | 输入前是否清空 | ○（纠错信号） |

> `backspaceCount` 与 `clearedBeforeTyping` 是**纠错信号**——用于区分"一次输入正确"与"修改多次后才正确"，是第 6.3 节判别器的输入之一。

### 5.3 元素定位快照

定位快照只需两个字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `xpath` | ✓ | **语义锚定的相对 xpath**，优先级见下 |
| `xpath_full` | ○ | 绝对路径，作为兜底 |

**`xpath` 的语义锚定优先级**：

1. 表单字段存在 placeholder → `//input[contains(@placeholder,'请输入客户名称')]`
2. 表单字段存在 label → `//div[contains(@class,'el-form-item')][.//label[contains(normalize-space(.),'客户名称')]]//input`
3. 图标按钮 → `//*[@aria-label='转交' or @title='转交']`
4. 按钮 / 链接文本 → `//*[normalize-space()='提交']`
5. 弹窗 / 抽屉内元素 → 以 `//div[contains(@class,'el-dialog') or contains(@class,'el-message-box')]//…` 或 `//div[contains(@class,'el-drawer')]//…` 包裹

> **约束**：不得以带索引的路径（如 `/div[3]/ul[2]/li[5]`）充当语义 `xpath`——该形态属于 `xpath_full`。二者的区分直接决定回放命中率。

> **说明**：动作类型（点击 / 输入 / 选择等）与元素用途归类，均属语义判断，按原则 P3 由**服务端**依据事件序列推断，采集端不做归类。定位质量不依赖采集端自报的置信度标记，而由服务端依据实际回放命中结果统计（见 7.1）。

### 5.4 页面标识

```
page:{scheme}://{netloc}{path}#{fragment 去掉 ? 之后的 query}
```

**须丢弃 query 参数**（含 `#` 片段内部的）。原因有两点：query 通常易变（时间戳、令牌、分页状态）；且带 query 的长 URL 会超出 `screenshot.level_key` 的 `VARCHAR(512)` 限制，导致**整条页面级记录插入失败**（既有实现见 `scripts/state.py:320` `page_level_key_from_url`）。

弹窗标识：`{pageKey}|dialog:{弹窗标题}`；同标题多实例时追加 `@@{anchor}` 区分。

### 5.5 采集范围

**采集**

| 内容 | 用途 |
|---|---|
| 每个事件的绝对时间戳 | 间隔可事后推导 |
| 元素定位（语义 `xpath` + 绝对路径兜底） | 决定回放能否命中 |
| 页面标识 | 归集与区域归属 |
| 业务单号（正则提取） | 补 `biz_key_prefix[]`（稀疏率 0.83） |
| 异常提示（toast / 校验红字） | 补 `exceptions[]`（0.63）；同时是成功判定的依据 |
| 网络元数据（path + 状态码） | 判断提交是否真正成功 |
| 操作内行为（退格数、清空重填、输入耗时、blur 时机） | 纠错信号，用于噪声过滤 |

**不采集**

| 内容 | 原因 |
|---|---|
| 操作**之间**的间隔、停留时长 | 无消费方。回放等待已是条件驱动（`_wait_if_loading` 走 `JS_CHECK_LOADING` → `JS_WAIT_LOADING` 等待遮罩消失，优于固定时长），且间隔可由时间戳推导 |
| 暂停 / 继续功能 | 与「结束 + 开始」等价（同为两次点击），且不提供额外能力 |
| 任何需要用户输入的业务语义字段 | 用户不熟悉本系统的分类体系 |

> **区分**：时间维度中值得保留的是「**单次操作内部的行为痕迹**」（退格、清空重填），而非「操作之间的等待」。前者是纠错信号，属于操作步骤的细节；后者无消费方。
>
> **收敛原则**：绝对时间戳必采（零成本），派生字段（间隔、停留）不采（可由时间戳推导）。

### 5.6 幂等与脱敏

**幂等**：以 `(externalSessionId, segmentIndex)` 为唯一键。插件侧重试属常见情况，重复投递须被识别而非产生重复证据。

**脱敏逐项**

| 字段 | 要求 |
|---|---|
| `operatorRef` | 哈希或工号引用，非姓名 |
| 输入类值、`triggerValue`、before/after | 自由文本须脱敏；枚举名（如"流动资金贷款"）可保留 |
| `exceptionText` / `rejectReason` | 通常含业务数据，须脱敏 |
| `bizKey` | **保留**——属业务标识而非个人信息，且是跨会话关联的关键 |
| 网络数据 | 仅 path 模板 + 状态码，丢弃 query 与 body |
| 页面结构摘要 | 仅字段名与列名，不含字段值 |

**原则**：采不到即留 `null`，不推断、不填默认值。此约束在"该步是否成功"一类判断字段上尤为关键——服务端的自动断言会消费这些字段，将"未观测到"记为"成功"会使度量整体失真，且比没有度量更危险。

### 5.7 准入校验规则

服务端 L0 层的拒绝规则。**原则：结构性问题整包拒绝（否则归集会错乱），字段级问题仅丢字段（避免浪费已采集数据）。**

| 规则 | 处置 |
|---|---|
| `segmentIndex` 不连续 | 整包拒绝 |
| `pageLevelKey` 格式不符或含 query | 整包拒绝 |
| `sutVersion` 缺失 | 整包拒绝 |
| 会话时间跨度 > 12h | 整包拒绝（同时作为插件心跳异常的探针） |
| `segments` 数量超过 2000 | 返回分片提示 |
| `locator` 片段缺 `xpath` | 丢弃该片段，其余照收 |
| `ts` 超出会话起止范围 | 丢弃该片段 |

## 6. 服务端设计

### 6.1 存储模型

新增**语料层**，与既有的 `trajectory` / `phase` / `trajectory_step` 交易模型**并列**（而非嵌入）：

```
tester_trace_session      会话头（externalSessionId 唯一键、SUT 版本、操作员引用、时间范围、verdict…）
    └── tester_trace_segment   片段（session_id + segment_index 唯一键、原始 JSON、页码、时间戳）
    └── tester_trace_evidence  证据（归集产物：目标卡字段、来源片段 id、置信度、审核状态）
```

**为什么与交易模型并列而非嵌入**：语料是**片段形状**（重复、试错、断头路、非原子交易），与交易模型（一笔完整的、有阶段划分的业务操作）的结构假设不符。强行嵌入会导致语料被迫"凑成交易"，丢失大量有价值片段。

**语料层为只读**：不提供编辑入口；按保留策略过期清理。审核与晋升产生的记录写入证据层与知识层，语料层仅作为出处锚点的引用目标（对齐现有 `req_source_hash` / `req_chunk_id` 的出处锚点做法）。

### 6.2 处理流水线

```
投递 → L0 准入校验（自动，拒绝制）
     → L1 归一化落库（语料层，只读）
     → L2 证据归集 + 冲突检测 + 分流（自动）
     → L3 人工审核（审查表驱动）
     → L4 晋升 + 回归门禁（自动）
```

| 层 | 内容 | 执行方 |
|---|---|---|
| **L0** | 格式、schema、幂等去重、脱敏复核、会话下限 | 自动，规则见 5.7 |
| **L1** | 按 `segmentType` 分桶落库。**不做任何语义判断** | 自动 |
| **L2** | 归集、冲突检测、频次统计、分流 | 自动 |
| **L3** | 审查表逐条裁决 | 人工 |
| **L4** | 写回知识层 + 复跑门禁 | 自动 |

**L2 的具体职责**（机械部分全部自动，对齐 `scripts/kb/promote.py` 的既有分工："机械部分由本模块完成；审核决策在人"）：

1. 按 `pageLevelKey` / 关键词将证据归集到候补卡
2. 按**证据目标字段**分桶（该证据支持 `field_deps` 还是 `state_actions`？）
3. **冲突检测**：与现有卡矛盾时生成 candidate 记录并**挂起**，不自动覆盖
4. **频次统计**：同一证据被多少个不同会话、多少个**不同操作员**独立观察到

> **独立操作员数是置信度的关键指标**——同一人重复 100 次的证据强度低于 5 人各做 2 次。

**L4 的回归门禁**（既有纪律：任何召回输入变更须复跑评测并与基线 diff）：

- KB 召回评测 `scripts/kb/recall-eval.mjs`
- 覆盖率快照 `scripts/kb/kb-coverage.mjs`

### 6.3 反馈判别器

这是本设计中最核心的一条判定规则，用于区分"用户的纠错"与"系统的拒绝"。

| 情况 | 系统是否有反馈 | 处置 |
|---|---|---|
| 点错字段后改点正确字段 | 无 | **仅保留最后一步**，前一步不生成 |
| 输入错误后清空重填 | 无 | **仅保留终值** |
| 走错路径，点入无关页面 | 无 | **该步骤不生成** |
| 留空提交 → 系统提示"利率不能为空" | 有（校验红字） | **保留** → `exceptions[]` / `rules[]` |
| 已审批单据点击修改 → 系统拒绝 | 有（toast） | **保留** → `rules[]` / `state_actions[]` |
| 点击某按钮无反应（元素 `disabled`） | 无，但元素本身 `disabled` | **保留** → 前置条件证据 |

> **规则**：**无系统反馈的用户纠正 = 噪声，折叠为最后一步；有系统反馈的拒绝 = 知识，完整保留。**

**该判别器的价值**：

1. **客观性**——完全由 DOM 状态、反馈提示与网络状态码判定，不需要向用户提问。
2. **可替换现有启发式**。当前 `_record_action`（`scripts/state.py:1006`）依赖特判（`scripts/state.py:1038` / `:1058` 两段，例如"若本次点击文本等于上一步 fill 的值，则判定为日期选择器重开噪声"）来推断用户意图。此类特判会随 SUT 漂移持续增长，应由本判别器替代。

### 6.4 证据归集与冲突检测

**证据目标字段**：卡本身是字段化结构，每个字段可独立被一段证据支持，**不要求片段拼成完整交易**。

| 证据类型 | 目标字段 | 审核级别 |
|---|---|---|
| 术语与同义表述 | `aliases[]` / `keywords[]` | 机械 + 抽检 |
| 页面到达与结构 | `nodes[].page` / `enter` / `structure` / `card_fields` | 抽检 |
| 业务单号 | `biz_key_prefix[]` | 抽检 |
| 前置条件 | `preconditions[]` | 抽检 |
| 异常提示 | `exceptions[]` | 抽检 |
| 字段联动 | `field_deps[]` | 抽检 |
| 状态×动作 | `state_actions[]` | **逐条人审** |
| 完整链路 | 频次排序 / 新卡提案 | 人审 |

**权威性与频次性是两个正交维度**：

- **权威性**（谁的说法优先）：湿测 > 需求原文 > 采集语料 > 卡面推断
- **频次性**（多常见）：**采集语料独有**——文档与湿测都不提供"某功能每天使用 500 次、另一功能三个月无人使用"这类信息

**冲突处理**：

| 冲突情形 | 处置 |
|---|---|
| 语料 vs 卡面 | 生成 candidate 并挂起，**不自动覆盖**（语料含误操作，卡面至少经过一次人工审读） |
| 语料 vs 湿测 | 湿测优先；**同时记录反例**——这往往是 SUT 版本漂移的早期信号 |

### 6.5 分流规则

| 数据类型 | 进路径先验 | 进异常/规则知识 | 语料层 |
|---|---|---|---|
| 用户纠错（无系统反馈） | 仅保留终态 | ✗ | 保留 |
| 反案例（系统拒绝） | ✗ | ✓ | 保留 |
| verdict = 不通过 | ✗ | ✓（含 bug 复现路径） | 保留 |
| verdict = 作废 | ✗ | ✗ | **插件侧已丢弃，不投递** |
| verdict = 通过 | ✓ | ✗ | 保留 |
| verdict 缺省（空闲超时自动收尾） | 降权参与 | 降权参与 | 保留 |

**重复测试的归并规则**（同一功能的多次会话）：

| 情形 | 处置 |
|---|---|
| 存在 verdict = 通过的会话 | 取 **verdict = 通过且时间最后**的一次作为正样本 |
| verdict = 作废 | 不作为证据（已在插件侧丢弃） |
| verdict = 不通过 | 作为异常证据 |
| 未作选择（空闲超时） | 降权参与，需多次独立会话相互印证后才可晋升 |

**"同一功能"的判定**由服务端完成：入口页 + 菜单路径 + 业务对象类型相同即视为同一功能。

**"不通过"为何必须保留**：用户的"不通过"判定是业务结果判断，而录制需要的是操作可达性，两者不等价：

| | 操作可达（路径可复现） | 操作不可达（中途卡死） |
|---|---|---|
| 业务通过 | 正样本：路径 + 结果断言 | 少见，通常为断言缺陷 |
| 业务不通过 | **高价值正样本路径**（bug 复现） | 弯路 / 前置条件 / 被拒规则证据 |

录制的内容是"操作步骤 + 操作的元素"，回放复现的是操作而非业务结论。因此"业务不通过但操作可达"的路径是完整且可回放的，其用途即"复现该缺陷"。若弃用反案例数据，录制时系统将不知道"未选行时转交按钮禁用""已审批单据不可修改"等约束，执行机会反复尝试不可用的操作——直接损害效率目标。此外，反案例是以下字段的唯一供给源：

| 字段 | 稀疏率 | 唯一来源 |
|---|---|---|
| `exceptions[]` | 0.63 | 反案例 |
| `rules[]` | 0.42 | 系统拒绝提示 |
| `state_actions[]` | 0.76 | 需要允许集合的边界，依赖拒绝观测确认 |

## 7. 消费设计

### 7.1 定位先验（服务准确性）

**产出**：按元素类别统计其语义 `xpath` 在**实际回放**中的命中率，并结合 xpath 的形态特征（是否为语义锚定、是否落在弹窗作用域内）做归因。

**消费方**：

- 回放的定位尝试顺序与候选生成（`scripts/controller/actions/_replay.py:453` `_resolve_replay_xpath`）
- 录入时的定位质量打分

**特性**：以回放结果为依据的统计量，客观、抗噪、无需人工审核，可最快见效。

### 7.2 路径先验（服务效率）

流程卡提供的是**静态知识**（页面含哪些字段、有哪些前置条件），不提供**动态路径**——从 A 页到 D 页实际如何走、在哪一步最常受阻。采集语料天然包含路径数据。

| 产物 | 说明 |
|---|---|
| **下一步动作推荐** | 在页面 X 上，历史上 80% 的操作者先点击 Y |
| **常见弯路标记** | 30% 的操作者会先点击 Z 然后失败退回。知道不可行的路径与知道可行路径同等重要——可使系统主动规避 |
| **步骤数期望 → 录制期偏移提示** | 若已知"该流程正常 12 步"，而当前录制已进行 30 步仍未结束，可实时提示 |

> **与既有能力的互补**：系统已有**反向**检测能力——开发者指南（`docs/superpowers/guides/ui-record-through-line-agent-prompt.md:81`）记录了"AI 若十几秒全 phase_done 且几乎无步骤 = 假成功"，该检测针对**录制步骤过少**。路径先验补充的是**录制步骤过多**的检测，而后者目前无任何机制覆盖（重复测试、绕行产生的冗余轨迹无法识别）。

### 7.3 知识晋升（补全卡字段）

按 6.4 的证据映射写回流程卡字段。晋升流程复用既有机制：

| 步骤 | 复用对象 |
|---|---|
| 机械聚类与草稿生成 | `scripts/kb/promote.py` |
| 审查表产出与写回 | `scripts/kb/promote_draft.mjs`（dry-run 产出 `tmp/*-review.md` → `--apply`） |
| 门禁复跑 | `scripts/kb/recall-eval.mjs`、`scripts/kb/kb-coverage.mjs` |

## 8. 审核机制

### 8.1 分层的必要性

不同片段的风险差异显著：`aliases` 出错仅影响召回质量；`state_actions` 出错会**主动误导录制**——执行机会认为某状态下某按钮可用，尝试点击后失败。后者比缺少知识更糟。

### 8.2 审核级别

| 级别 | 内容 | 执行方 |
|---|---|---|
| L0 机械拒绝 | 格式、幂等、脱敏、下限 | 自动 |
| L1 机械聚合 | 聚类、去重、证据归集、频次统计 | 自动 |
| L2 机械冲突检测 | 与现卡矛盾则挂起，不覆盖 | 自动 |
| L3 人工审核 | 审查表逐条裁决 | 人工 |
| L4 晋升回归 | 复跑召回评测 + 覆盖快照 | 自动门禁 |

### 8.3 审核要求

1. **高风险的 `rules[]` / `state_actions[]` 必须逐条人审**，不允许批量 `--apply`。
2. **审查表须显示独立操作员数**——这是审核人做判断时最重要的一个数字。
3. **低置信度的处置是挂起待内部处理，而非回头询问测试人员**。流程卡维护者熟悉本系统的分类体系，测试人员不熟悉，询问对象错误只会引入噪声。挂起的条目由 `promote.py` 的审查表机制消化。

## 9. 系统侧改造清单

按改动成本由小到大排列：

| # | 现状 | 问题 | 改造方向 | 成本 |
|---|---|---|---|---|
| 1 | 成功判定依赖人工 `confirmed` 与 LLM 推断（`trajectory_step.confirmed`；`src/services/trajectory/heal-decision.js:36` `routeSuggestedAction` 仅接收 `suggestedAction` 字符串） | 成功在多数场景下是可观测的（反馈提示、校验、跳转、网络状态），不应依赖推断。"元素未找到"与"业务校验未通过"在当前实现中无法区分 | 改为结果观测驱动。区分后：前者应 `retry`（重试有意义），后者应 `fail`（业务规则拒绝，重试无效）。**该区分不需要 LLM** | 小 |
| 2 | 噪声过滤依赖启发式特判（`scripts/state.py:1038` / `:1058`） | 特判持续增长且随 SUT 漂移失效 | 改由 6.3 判别器驱动 | 小 |
| 3 | 定位器是**录制时固化的字符串**；回放仅按 `xpath_smart` → `xpath_full` 两级尝试（`_replay.py:404` `_element_xpath_smart` / `:436` `_element_xpath_full`，路由在 `:453` `_resolve_replay_xpath`；`replay_click.py:33`）。既有录制数据中的 `candidates[]` 仅被作为字典查询两个键，**从不按序试用** | 定位质量是元素**类别**的统计属性，当前被当作单步的孤立对象 | 定位器由"录制产物"转变为"**回放时按统计生成的候选序列 + 跨会话命中统计**" | 中 |
| 4 | 召回为"一次查询一张卡"，不包含频次与路径信息 | KB 覆盖回溯已明确"按真实频次补缺口"，但召回本身未使用频次 | 卡片 + 频次/路径先验共同召回 | 中 |
| 5 | 数据模型为**交易形状**（`trajectory` → `phase` → `trajectory_step`） | 语料是**片段形状**，与交易模型的结构假设不符 | 新增 **fragment-native 语料层**，与轨迹层并列 | 大 |

> **第 3 项是最根本的改造**：定位器不应是录制产物。录制阶段应记录的是"这是什么元素、处于什么上下文"，具体使用哪个 xpath 应在回放时依据统计生成的候选序列**实时计算**。当前做法将一次录制的偶然定位结果固化为产品资产，这是定位准确率问题的结构性来源——既有录制数据中的 `candidates[]` 采集后未被使用，根源即在此。

## 10. 治理与红线

1. **评测集隔离**：语料不得进入 `scripts/characterization/fixtures/kb-recall-eval.v*.json` 或任何冻结 fixture。既有纪律为"扩充/修订评测集时禁止先跑匹配器反推 gold"；语料作为 gold 的污染更隐蔽。
2. **不自动覆盖冲突**：语料权威性低于湿测与需求原文，且含误操作。所有冲突一律挂起，人工裁决。
3. **脱敏**：沿用 `scripts/kb/coverage-snapshot.mjs` 的白名单脱敏口径。
4. **采不到即留 `null`**：不得将"未观测到"记为"成功"。服务端的自动断言会消费该字段，一旦失真，度量将整体失效且比无度量更危险。
5. **晋升后必须复跑门禁**：召回评测与覆盖率快照，与基线 diff 无回退方视为完成。
6. **语料可清理，知识可追溯**：晋升后的每条知识必须能回溯到语料证据（对齐现有出处锚点做法）。
7. **采集侧丢弃不可逆，服务端忽略可逆**（对应 P4）：仅「作废」场景在采集侧丢弃，其余一律投递并由服务端分流。

| 期 | 内容 | 验收口径 | 风险 |
|---|---|---|---|
| **P0** | 插件 v1（采集） + 服务端接入 + L0/L1 + **定位先验** | 候选降级链使回放定位成功率提升；副作用可量化 | 低（不涉及卡与评测集，无需人审） |
