# 评测与决策闭环（bench 口径 v1）

> **状态**：草案，待用户审阅。用户 10-30 提到的 bench P02 简报本文没有读到。如果 js-project 已有 bench，本文作为它的口径要求：已有的部分对齐命名即可，缺的部分补上。
> **用途**：让每个开关、每次引擎改动、每个复用组件都有一份可重复的「做 / 不做」数字结论；同时校准 AI 事后核验。
> **上游**：[`../reports/2026-10-30-tech-director-direction-review.md`](../reports/2026-10-30-tech-director-direction-review.md) 第五节 M1–M3。

## 1. 结论

- 评测由四部分组成：固定任务集、配对运行、分层成功指标、跑之前就写好的决策规则。
- 轨迹级成功率只用来判断大效应（约 20 个百分点及以上）。小效应看阶段级结果和连续指标：活跃耗时、模型调用数、重复步占比。
- AI 事后核验先校准、再当标签：人工盲标约 200 条，出混淆矩阵，核验器版本冻结。
- 尽量复用已有资产：`scripts/kb/kb-ab-eval.mjs` 的配对与收数做法、`characterize-kb-ab` 的协议门禁、`scripts/kb/coverage-snapshot.mjs` 的只读快照与脱敏。

## 2. 范围

**本文交付：** 任务集规范、运行协议、指标与口径、核验器校准协议、决策规则、报告格式。

**不在本文：** 执行机调度改造；前端看板（本文只定义数据）；具体任务清单（由维护人按 §3 的规则填写）。

## 3. 任务集

### 3.1 分层

| 层 | 内容 | 建议数量 | 作用 |
|---|---|---|---|
| R 只读 | 导航、查询、打开详情 | 8–10 | 复用 v1 与录后验证的主要对象；不弄脏数据，可以高频跑 |
| W1 单页写 | 单页新增或修改并保存 | 8–10 | 控件卡住、判定误判的主要发生地 |
| W2 多腿链路 | 跨菜单、多阶段 | 4–6 | KB A/B 显示提示类收益集中在这里 |
| X 已知墙 | 已知会被被测系统拒绝的任务（在途流程、角色无用户等） | 2–3 | 对照组：检验录前体检与失败归因是否正确 |

### 3.2 任务定义

每个任务一份 JSON，字段：

| 字段 | 说明 |
|---|---|
| `id`、`tier`、`version` | 任务标识、所属层、任务版本 |
| `systemId`、`functionId`、`accountRole` | 被测系统、功能节点、使用的账号角色 |
| `requirementText` | 交给录制的需求原文 |
| `businessData` | 业务数据；唯一字段必须给生成器（例如业务 stamp + 时间戳），保证可重复跑 |
| `expected` | L1 证据：成功 toast 文本、单据号正则、结束页面键等，至少一条 |
| `cleanup` | 清理方式；无法清理时写 `none`，并控制该任务的运行频率 |
| `knownWalls` | 已知的被测系统拦截（X 层必填） |

### 3.3 冻结与变更

任务集带版本号。改任务就升版本，并在新旧两个版本上各跑一次基线，做法同 KB 召回评测集 v1 → v2。

## 4. 运行协议

- **单一自变量**：每次对照只改一处（一个开关、一个改动、一个组件集合）。
- **配对与交替**：同一任务在两臂各跑，顺序交替（ABAB / BABA）；同一时间窗、同一执行机池、同一模型配置。
- **次数**：每个任务每臂至少 3 次；R 层可以更多。
- **记录**：runId、臂、任务及版本、代码 commit、提示词版本、模型名、核验器版本、开始与结束时间。
- **基础设施失败**：执行机异常、模型 5xx 之类的运行标为 `infra_fail`，单独统计并报告占比，不计入成功率分母。

## 5. 指标与统计

### 5.1 指标

| 指标 | 粒度 | 来源 |
|---|---|---|
| 成功 L0–L3 | 轨迹 | `record_status`；L1 由 `expected` 证据判定；L2 由录后验证；L3 为人工确认 |
| 阶段成功 | 阶段 | 阶段结果、`gate_decision` |
| 活跃耗时 | 轨迹、阶段 | 步骤时间戳，剔除超过 10 分钟的停顿（口径同 09-24 报告） |
| 模型调用数 | 轨迹、阶段 | 需要埋点：每次调用记 runId 与角色（主模型、规划、场景摘要、识图、表单、评审、事后核验） |
| 重复步占比 | 轨迹 | 同阶段、同动作、同参数 |
| 失败归因 | 轨迹 | `failed_kind`、reviewFlags、`gate_decision` |
| 复用指标 | 阶段 | `operation_component_use`（复用设计稿 §5.2） |

### 5.2 样本量

双侧 α=0.05、检验功效 0.8、两比例检验、不配对时，每臂需要的轨迹数：

| 基线成功率 | 要检出的提升 | 每臂所需轨迹数 |
|---|---|---|
| 65% | +30 个百分点（→ 95%） | 约 27 |
| 65% | +20 个百分点（→ 85%） | 约 73 |
| 65% | +10 个百分点（→ 75%） | 约 329 |

含义：25–30 个任务、每臂各跑 3 次（约 75–90 条），只够判断 20 个百分点量级的变化。10 个百分点量级的改动，要么多轮累计，要么改看阶段级结果和连续指标。配对设计在任务难度主导方差时能减少所需样本（按不一致对做 McNemar 检验）。耗时这类连续指标，检出「中位数减半」通常 20 对左右就够。

### 5.3 核验器校准的样本量

要把约 0.85 的比例估计到 95% 置信区间半宽约 ±7 个百分点，需要约 100 条（1.96² × 0.85 × 0.15 ÷ 0.07² ≈ 100）。所以判正常、判异常两类各抽约 100 条。

## 6. 核验器校准协议

1. **抽样**：从近期终态轨迹中按核验结论分层抽样，判正常、判异常各约 100 条；覆盖 R、W1、W2 三层任务与主要失败类别。
2. **盲标**：标注人看步骤、截图和业务证据，给出「正常 / 异常 / 无法判断」，看不到核验结论。20% 由两人交叉标注；一致率低于 0.8 时先统一口径再继续。
3. **计算**：混淆矩阵；异常类的精确率与召回率；按任务层分别报告。
4. **准入**：异常精确率 ≥ 0.9 且召回率 ≥ 0.7（建议值，待裁）时，核验结论可以继续直接改写录制状态；否则改为只写待复核标记，不改状态。
5. **冻结**：核验提示词与模型带版本号。换版本必须在同一标注集上重跑并对比。
6. **复检**：每次换版本，或每月一次，从新数据再抽约 50 条复检。

## 7. 决策规则

规则要在跑之前写定，跑完按规则出结论，不事后调整口径。

**「未见劣化」的操作定义（建议，待裁）**：两臂 L1 成功率之差 ≥ −5 个百分点；并且按任务配对，3 次中比对照臂少成功 2 次及以上的任务不超过任务总数的 10%。样本量不足以证明「不劣」时，结论写「未见劣化」，不写「不劣」。

| 场景 | 规则 |
|---|---|
| 默认关闭的开关是否转为默认打开 | 未见劣化，且目标指标显著改善 → 打开；未见劣化但目标指标无改善 → 不开，记录结论；劣化 → 不开并回查原因 |
| 新增或修改一道门 | 用 `gate_decision` 统计该门的拒绝次数与「被拒后最终成功」比例，并抽样人工判定误拒；误拒率超过约定值不得默认打开 |
| 引擎改动合入 | R 与 W1 层未见劣化，改动针对的指标有改善 |
| 复用 v1 | 见复用设计稿 §11 |
| 停止投入 | 同一方向连续两轮评测都没有改善，结论写明停止 |

## 8. 报告

- **每轮一份**：`docs/superpowers/reports/bench/<日期>-<轮次>.md`，原始数据另存 JSON。
- **每轮内容**：版本信息（代码、提示词、模型、核验器、任务集）；两臂 L0–L3 成功率与配对差值；阶段级结果；耗时与模型调用数的中位与 P90；失败归因分布；`infra_fail` 占比；按 §7 规则逐条写出结论。
- **滚动趋势**：最近四轮的成功率、耗时、模型调用数、复用命中率。
