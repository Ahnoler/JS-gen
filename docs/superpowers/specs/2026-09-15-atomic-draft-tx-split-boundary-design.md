# 原子化组件草稿交易 — 拆分边界设计

> 日期：2026-09-15  
> 状态：已审阅；实现按 2026-09-16 plan（PR #37）；2026-09-16 补 prompt 层「能力内聚」（无场景关键词硬闸）  
> 决策：方案 B（结构化 `produces` / `dataDependsOn` + 短通用规则）  
> 相关：`2026-09-07-req-to-draft-traj-design.md` §3 粒度；`2026-09-09-flow-card-guided-propose-design.md`；线上 prompt `scripts/prompts/req-draft-traj-atomize-prompt.md`；湿测对照 #675 / #676 / #678 / #504 / 维护形态 #708

## 1. 背景与问题

`draft-traj/propose` 需要把需求切成**可独立录制的组件级草稿交易**。此前用「产品树每层新增各成 atom」等场景特例加固 prompt，适用面窄，离开该业务即失效。

目标：用**通用拆分边界**定义标准粒度，使切分与校验不依赖具体菜单/树层级文案。

湿测对照（摘要）：

| traj | 角色 | 要点 |
|------|------|------|
| #675 | 正例 · 新增一级 | 仅一次新建落库；`produces` 一级；无上游数据依赖 |
| #676 | 正例 · 新增子分类 | 选中已有一级后新建子类；依赖一级 |
| #678 | 正例 · 新增产品 | 展开/选中已有节点后新建产品；依赖一级+子类 |
| #504 | 写法污染 | 单交易内嵌「找不到父则先造父」兜底，且按钮口径错误致幽灵顶层 |

## 2. 目标与非目标

### 2.1 目标

1. 明确「一笔 atom = 一个可独立录制的组件交易」的操作定义与拆分主规则。  
2. 用结构化字段表达产出与依赖，使 prompt 与 `propose.js` 可机检。  
3. 修订 atomize prompt：通用依赖语言；禁止场景特例清单与 #504 式本笔造上游。  
4. Characterization：自产自依赖拒、悬空依赖拒、合法依赖链过。

### 2.2 非目标（本版不做）

- 「一笔最多一次【确定】」硬闸（原方案 C）。  
- 从 `taskDraft` 自动推断并改写 `produces` / 自动重切。  
- 录制运行时按 `dataDependsOn` 强制调度执行顺序。  
- 批量回放、操作组件沉淀、引擎合约改动。  
- 按产品树层级 / 菜单路径 / 业务关键词强制拆笔。
- 为具体按钮文案（排序/维护等）增加硬拒；能力内聚只写在 prompt + 样例（§3.7）。

## 3. 核心模型（拆分边界）

### 3.1 独立录制

一笔 atom 在其**前置草稿交易已完成**（或依赖数据已环境/人工预置）的前提下，**单独开录应能跑通**。

### 3.2 字段

每笔 atom 增加（名称固定语义；实现可用等价命名但文档与 prompt 统一用下列名）：

| 字段 | 含义 |
|------|------|
| `produces` | `string[]`。本笔落库成功后**新确立**、可供下游引用的关联数据键。只列本笔新建或本笔修改所确立的对象；**不列**仅被搜索/选中的已有对象。 |
| `dataDependsOn` | 本笔开录前必须已存在的关联数据。元素为键名字符串，或 `{ "key": "...", "source": "atom" \| "preset" }`。`source` 缺省视为 `atom`（须由同批其它 atom 的 `produces` 提供）。 |
| `preconditions` | 可选。非数据键的环境前提（如已登录），与 `dataDependsOn` 分工。 |
| `taskDraft` | 可执行录制步骤文案；须与上表同构。 |

### 3.3 必须拆（唯一主规则）

若步骤 B 要新建/修改的对象，其输入依赖步骤 A 所 `produces` 的数据，则 **A 与 B 不得同一 atom**；B 的 `dataDependsOn` 指向 A 的 `produces`。

同 atom 内**禁止**「先 `produces` X，再依赖 X 做下一步新建」（自产自依赖）。

### 3.4 允许合进同一笔

- 进入功能页、等待加载。  
- 搜索 / 展开 / 选中 **已存在** 的 `dataDependsOn` 对象（来自已完成前置草稿或预置）。  
- 同一次落库闭环：打开同一新建/修改入口 → 填多个字段 → 一次【确定】/保存成功。  
- 以上合入仅限**同一项业务能力**（§3.7）；另一项可独立验证的能力即使同页也须另起 atom。

### 3.5 禁止写法

- 业务场景特例清单（例如「产品树每一层必须拆」）。  
- `taskDraft` 内「若找不到上游对象则先新建该上游再继续」（#504 式兜底）。缺上游应拆出上游 atom，或标 `source: "preset"` 并由人保证预置。

### 3.6 对照示例

| atom | produces | dataDependsOn |
|------|----------|---------------|
| 对齐 #675 | `[一级分类]` | `[]` |
| 对齐 #676 | `[子分类]` | `[一级分类]` |
| 对齐 #678 | `[产品]` | `[一级分类, 子分类]` |

### 3.7 能力内聚（prompt 层；无关键词硬闸）

`produces` / `dataDependsOn` 处理「谁先于谁」。**能力内聚**处理「同页步骤是否属于同一项可独立验证的业务能力」：

1. 一笔 `taskDraft` = 一项业务能力、一个主产出、一次落库闭环。  
2. 准备步骤仅当服务于该项能力时允许并入：定位 `dataDependsOn`、打开表单、填写该项能力的字段。  
3. 禁止把另一项可独立验证的能力写进同一草稿，即使同页、同一对象、同一需求段落。

不把具体按钮文案或树层级写入硬闸；既有闸是 `missing_depend_fields` / `self_produce_depend` / `dangling_data_depend` / `multi_persist_task_draft`。场景特化关键词拒已放弃，改由本条通用规则约束。

直觉对照（非场景法）：维护已有对象 = 定位 + 编辑该项能力字段 + 一次保存为一项能力；列表上另一次可独立验收的操作与详情保存是不同能力。互相依赖的新建仍由 §3.3 依赖图拆分。

## 4. Prompt 职责

`scripts/prompts/req-draft-traj-atomize-prompt.md`：

1. 要求每笔输出非空 `produces`、连贯 `dataDependsOn`、`taskDraft`（及既有字段）；prompt 以 XML 分区（`<role>` / `<output_contract>` / `<split_rules>` / `<examples>` / `<anti_patterns>` / `<checklist>`）承载合同与 few-shot。  
2. 用 §3 主规则指导切分；允许「进页 → 对依赖键先搜索/定位再选中 → 一次落库」。  
3. 禁止场景特例清单与 #504 式本笔造上游。  
4. 文末「关键数据」KV 键名与 `produces` / `dataDependsOn` 一致。  
5. 保留：禁止系统菜单导航；一功能可录闭环优先等既有合理规则中与 §3 不冲突者。  
6. 用 §3.7 能力内聚约束同页多能力：一笔一项能力；准备步骤从属该能力；禁止夹带另一项可独立验证的能力。不把按钮文案写入硬闸。

**搜索先于写**：对 `dataDependsOn` 中的键，新建/修改前须先尝试搜索或树/列表定位再操作——属 **atom 内写法**，不是按业务对象类型强制拆笔的特例。

## 5. propose.js 校验范围

| 级别 | 条件 | 行为 |
|------|------|------|
| 硬闸 | 物化后 `produces` 为空（字段缺失、`[]`、或仅空白键） | 该 atom `rejected`，原因：`missing_depend_fields` |
| 硬闸 | 同一 atom：`produces` ∩ `dataDependsOn`（按 key）非空 | 该 atom `rejected`，原因：自产自依赖 |
| 硬闸 | `dataDependsOn` 项 `source` 为 atom/缺省，且同批无任何 atom 的 `produces` 含该 key | `rejected`，原因：依赖悬空 |
| 通过 | `source: "preset"` | 不要求同批 `produces` |
| 通过 | 根 atom `dataDependsOn: []` 且 `produces` 非空 | 合法 |
| 硬闸 | `taskDraft` 内多次落库确认 | `multi_persist_task_draft`（既有） |
| 不做 | 产品树层级 / 关键词强制拆 | — |

**兼容**：旧客户端可忽略新字段；新 prompt 仍要求模型输出。物化后 `produces` 为空硬拒 `missing_depend_fields`，不得静默当合法依赖链。

**与 flowCards**：有卡时仍可参考卡上可录闭环；**冲突时以 §3 依赖规则为准**。卡若将「造 A + 造依赖 A 的 B」画在同一闭环，仍须拆成两笔并用 `dataDependsOn` 串联。`flowRef` / `nodeId` 能挂则挂，不能挂不伪造。

## 6. taskDraft 同构规则

1. 步骤中搜索/选中/展开的对象 ∈ `dataDependsOn`（或标明预置）。  
2. 本笔【确定】后新确立的对象 ∈ `produces`。  
3. 禁止只在散文提依赖却不进入 `dataDependsOn`。  
4. 开头允许进功能页与等待加载；禁止系统菜单导航。

## 7. 错误处理小结

见 §5。flowCard 与依赖规则冲突导致拆笔时：保留可挂的卡引用；不因缺卡失败（无卡模块仍须能 propose）。

## 8. 验收口径

1. Prompt + propose 载荷含 `produces` / `dataDependsOn`；规则为通用依赖语言，**无**产品树层级特例。  
2. #675/#676/#678 同构夹具：三笔依赖链通过硬闸；故意合成「一级+子类+产品」一笔则因自产自依赖或等价违规被拒。  
3. Prompt 禁止项含 #504 式本笔造上游。  
4. 无卡模块 propose 不因缺卡失败。  
5. Characterization：自产自依赖拒、悬空依赖拒、合法依赖链过。  
6. Prompt + 样例含通用「能力内聚」三条；**无**排序/维护等按钮文案硬闸。
